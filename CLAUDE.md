# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
bun run src/index.ts        # run the server (default 127.0.0.1:7682)
bun run typecheck           # tsc --noEmit
bun test                    # full suite (typecheck is NOT included here)
bun run test                # typecheck + bun test — what CI effectively does
bun test src/geometry.test.ts            # one file
bun test src/tmux/                       # one directory
bun test -t "dragging down by one line"  # one test by name
```

Bun only — no build step, no bundler. `src/index.ts` is the `bin` entry and ships as uncompiled TypeScript; node cannot run this package. tmux 3.2+ is required and startup refuses to run below it (`refresh-client -C <cols>,<rows>` comma form).

Publishing: push a `v<version>` tag matching `package.json`; `.github/workflows/publish.yml` publishes to npm via OIDC trusted publishing (no token, no OTP).

## Architecture

Browser (xterm.js) ⇄ WebSocket ⇄ Bun server ⇄ `tmux -C attach` (control mode) ⇄ tmux server.

**Control mode, not a PTY running `tmux attach`.** tmux speaks a structured protocol: output arrives per-pane as `%output %3 …`, and commands have request/response semantics. That is what lets the browser render one pane with no tmux status bar or split borders. `ControlClient` (`src/tmux/control-client.ts`) owns the subprocess; responses are matched to requests by a FIFO queue because tmux returns blocks in send order. `ControlParser` is the pure, DOM-free protocol parser.

**One browser connection = one disposable grouped session.** `PaneSession.open()` creates `web-<pid>-<random>` via `createWebSession`, attaches a control client to it, seeds the browser with `capture-pane`, then forwards live output batched at 16ms frames. On close it destroys the session and runs `resize-window -A` to hand the size back to remaining clients. The pid in the name makes orphan collection decidable from outside the process — `reapOrphanWebSessions` runs on startup and every 60s (`src/tmux/session-manager.ts`).

**The seed must restore terminal *modes*, not just content.** `capture-pane` returns text; the seed's `\x1b[2J\x1b[H` clears modes. Without replaying the mouse-tracking DECSETs (`mouseModeSeed`, driven by tmux's `#{mouse_*_flag}`), a program that uses the mouse comes back with tracking off and xterm never binds its wheel handler — scrolling silently dies.

**Server** (`src/server.ts`): a single `fetch` dispatching on pathname (no route table), plus the `/ws` upgrade. All state modules under `src/` are leaf modules it composes. Static files come straight from `public/`, and xterm.js is served out of `node_modules/`.

**Front-end** (`public/`): plain ES modules loaded directly by the browser, no framework, no build. UI strings live in `public/i18n.js` — never inline. `src/i18n.test.ts` scans every `t("…")`, `tr("…")` and `data-i18n` against both dictionaries and fails on a key that is missing, a key that is unused, or a key present in one language and not the other. That last case is the one worth having: a key missing from English is invisible to a Chinese-speaking author. Pure logic that can be tested headlessly (`scroll-gesture.js`, `terminal-fit.js`, `dir-filter.js`, `copy-on-select.js`) is split into `// @ts-check`ed modules with JSDoc types and tested from `src/*.test.ts`; the DOM-heavy ones (`terminal.js`, `list.js`, `create-sheet.js`) are not type-checked (`checkJs: false` in tsconfig).

**Page-level features are plugins, and the kernel never names one.** A plugin is one directory under `plugins/<id>/`: an isomorphic manifest (`plugin.js`), a server entry (`server.ts`), and its own `public/`. The kernel reads a hard-coded array in `plugins/registry.js`, dispatches `/api/<id>/*` to that plugin's handler, and serves `/p/<id>/*` from its `public/`. Grep `src/` for `jira`, `gallery` or `notifications` and the only hits are comments about push notifications, which is a kernel concept of the same name. Three exist: the artifacts gallery, the notification history, and Jira issues.

**Everything the kernel needs to know about a plugin comes from the manifest.** `titleKey` and `icon` build its tab; `i18n` merges into both dictionaries; `legacyPaths` declares addresses it occupied before it was a plugin, and the kernel answers those with a 301 to `p/<id>/`; `page: { mainId }` asks the kernel to generate the page shell. None of that is a table in the kernel keyed by plugin name, and none of it should become one — a capability that needs a kernel-side list of plugin names is a capability designed wrong.

The legacy-path redirect is deliberately checked **after** the static-file lookup, so a real page always wins. Order is what stops a plugin declaring `legacyPaths: ["index.html"]` from hijacking the app root; a validation rule could be argued around, an ordering cannot.

**A plugin ships its own stylesheet.** `plugins/<id>/public/style.css`, served like any other file in that directory and linked by the shell when it exists. It used to live in the kernel's `public/style.css` — eighty-odd lines of it — which meant deleting a plugin left orphan rules nobody could attribute. Colours still come only from the theme variables, and `src/themes.test.ts` now enforces that across the kernel sheet *and* every plugin sheet: it carries an explicit list of the literals that already existed, so the rule bites on anything new while the existing debt stays visible and finite rather than invisible.

**The page shell is generated unless a plugin opts out.** That block — viewport, the `use-credentials` manifest link, icons, stylesheets, the header container — was copied into three files that had to stay byte-identical, with nothing checking that they did; dropping `crossorigin` makes PWA installation fail silently behind an authenticating proxy. A plugin that needs more markup ships its own `public/index.html` and the kernel serves that instead. The gallery does exactly this, for its full-screen viewer — the escape hatch has a real user, which is the only reason to keep it.

**Two tables, and it has to be two.** `plugins/registry.js` is isomorphic — `i18n.js` merges plugin dictionaries from it and `nav.js` builds tabs from it — so it must never import a `.ts`, or server code lands in the browser bundle. The server side therefore lives in `plugins/handlers.ts` as `SERVERS`, one entry per plugin declaring what it can do (`handle`, `enrich`). Static imports need literal paths and runtime `import()` is banned, so the second entry cannot be derived. `plugins/registry.test.ts` asserts the two stay in sync in both directions — a manifest with no server entry is a tab whose every API 404s, which is only discoverable by running it.

The manifest and the handler are deliberately two tables. `registry.js` is loaded by the browser (`i18n.js` merges plugin dictionaries, `nav.js` builds the tabs from it), so importing a `.ts` from it would drag server code into the browser bundle — `plugins/registry.test.ts` asserts its import graph contains none.

Nothing is loaded at runtime: no scan of `~/.tmux-next/plugins`, no dynamic import. This service has no auth and binds loopback; a plugin directory anyone can drop code into is a different threat model than the one in SECURITY.md. `TMUX_NEXT_DISABLE_PLUGINS=<ids>` turns one off — its tab, its API and its pages all disappear together.

A plugin owns its own disk state through `pluginStateDir(id)` (`TMUX_NEXT_<ID>_DIR`, else `~/.tmux-next/<id>`), but it does not necessarily own everything it displays: `notifications.jsonl` is written by the push pipeline (`src/push.ts`), and `src/notifications.ts` stays in the kernel for that reason. The plugin holds the page and the read route only, so disabling it stops the history page and not the notifications.

`safeBasename` (`src/safe-name.ts`) is kernel-owned for the same kind of reason, even though nothing about it is plugin-specific. It started inside the gallery module, and `src/upload-file.ts` — session file upload, a kernel feature — imported it from there, which made the kernel depend on a specific plugin: deleting that plugin directory would have stopped a kernel route compiling. The guard has no plugin semantics, so it moved to a leaf module three call sites now share (session upload, gallery upload, the plugin-asset route).

**Pull requests come from Jira; build status cannot.** An issue's PRs are answered by Jira's dev-status endpoint using the token already configured, so the PR list costs no new credential. Build status is a different story: this instance's `build.overall.count` is always 0 because CircleCI never reports into Jira. The checks are attached to the PR in Bitbucket instead, so the second hop asks Bitbucket — chosen over CircleCI's own API because it is per-PR and CI-agnostic (the same response carries CircleCI and Codacy alike, and it keeps working when a PR lives in another repo, which a CircleCI project slug does not). That hop needs a Bitbucket app password, which is why `SECURITY.md` now has a paragraph about scoping one to reads.

A failure in the second hop never removes the first: a PR whose checks could not be fetched is returned with `checksKnown: false`, and the page shows that as "not asked" rather than as "no checks". The two are different facts — one is about the PR, the other is about us — and collapsing them would make the page lie in the direction of looking tidy.

**Merge-conflict status is not available, and this is the evidence rather than a guess.** Bitbucket Cloud's public v2 API does not carry it: a pull request fetched with `?fields=%2B*` returns 30 fields, of which the only merge-adjacent ones are `merge_commit` and `merge_in_progress`, both null on an open PR. `/pullrequests/{id}/diff` cannot stand in for it either — it is a three-dot diff, so it returns 200 with a normal diff whether or not the branches would merge, which was confirmed against nineteen open PRs. The web UI does know, but it asks a private endpoint that an app password cannot reach: `api.bitbucket.org/internal/…` answers 403 and `bitbucket.org/!api/internal/…` answers 401. Reaching it would mean storing a full browser session for Bitbucket in a service that has no authentication of its own — a much larger credential than the app password, on an interface with no compatibility promise. The only public way to get a real answer is to attempt the merge, which is a write. So: not offered. If a proxy is ever wanted, "behind the destination branch by N commits" is computable from `destination.commit` plus the branch head, and is honest about being a risk signal rather than a conflict.

**Dev data is refreshable one issue at a time, and that is not a convenience.** A full sweep is one dev-status call per issue plus one Bitbucket call per PR — for fifty issues that is well over a hundred requests, which is why the results are cached for five minutes and the page does not re-fetch them on every open. `GET /api/jira/dev?id=<issueId>&refresh=1` re-asks about exactly one issue, which is what someone watching a single PR's build actually wants. Note the parameter is Jira's numeric **issue id**, not the key: dev-status does not accept keys, which is why `Issue` carries `id`.

**Shared browser modules resolve URLs against the app root, not the page.** Everything is relative so the app can be mounted under a reverse-proxy subpath, but a relative `fetch("api/…")` in a shared module resolves against whatever page loaded it — and plugin pages live at `/p/<id>/`. `public/root.js` derives the root from its own `import.meta.url` (it is always at the root, and it is served under whatever prefix the app is); `url("api/…")` is correct at any page depth under any prefix. Reaching for an absolute path instead is what breaks subpath deployment.

**Plugin pages are not `@ts-check`'d, and that is not laziness.** A plugin page's import specifiers are written for the URL it is served at (`/p/<id>/`, two segments deep), not the path it lives at on disk (`plugins/<id>/public/`, three deep) — `public/` is a directory that exists on disk and never in a URL. tsc's on-disk resolver cannot follow `../../i18n-apply.js` to the real `public/i18n-apply.js`, and `moduleResolution: "bundler"` offers no remap for it. The browser is the side that has to work, so the browser's resolution wins. This is also why `src/public-parses.test.ts` carries a small `Bun.build` resolver plugin that mirrors the server's URL→disk mapping so the bundler sees what a browser would; if `src/server.ts`'s plugin routes ever change, that resolver has to change with them.

**A plugin may export `enrich(items)` to hang read-only facets on a work item's card** (`plugins/handlers.ts`'s `ENRICHERS` table; `collectFacets` is the call site). This used to be `annotate(sessions) → text` — free-form display text glued to a session row — and it evolved rather than got replaced because the safety valve underneath it was already right: a 300ms hard timeout raced against the call, wrapped in try/catch, with one failure semantic (can't get it in time → there are none, the page still renders). `src/plugin-enrich.test.ts` (renamed from `plugin-annotate.test.ts`) still holds that line with a fake plugin that throws and one that hangs forever, and `collectFacets` still takes its enricher table as an optional parameter instead of reading `ENRICHERS` directly, for the same reason: the registry is a compile-time constant, and without injecting a fake entry there is no way to prove the timeout and the try/catch actually fire. What changed is the shape and the target. The target moved from a session to a work item, because a plugin's opinion (Jira's status, its PR checks) is a property of the *unit of work*, not of whichever tmux session happens to be attached to it right now. The shape moved from a string to `Facet = { dim, value, tone? }` — a small structured fact instead of a sentence — so the view layer can group and filter by it instead of just displaying it. Output is still capped at the kernel side, not trusted from the plugin: `dim`/`value` truncated to 120 characters, any item id not among the ones actually asked about dropped, and a new cap on top — `MAX_FACETS_PER_ITEM` (6) — applied *after* merging every plugin's facets for an item, not per plugin, so two enabled plugins can't together flood one card even though neither alone would.

**`Facet.dim` is an i18n key, not display text, and that one choice is what keeps the kernel from ever needing a table of "which plugin owns which dimension".** `jira.status` and `jira.epic` merge into the dictionaries the same way `titleKey` does, and `tr(dim)` at render time is what turns the key into a label — falling back to the raw `dim` string if no translation exists, so an unlisted dimension degrades instead of breaking. `public/facet-view.js` and `public/items.js` compute their groups and filters from whatever `dim`/`value` pairs show up in the data (`dimensionsOf`, `valuesOf`) — there is no hard-coded dimension list anywhere in the view, which is the actual point of routing the name through the data instead of through a manifest field the kernel reads. The one place a dimension's name has to be written down as a literal is `src/i18n.test.ts`'s dead-key scan, because `tr(facet.dim)` is a dynamic lookup and the scanner only recognizes string literals — it cannot see a key arriving with the data. Kernel dimensions (`item.agent`, `item.sessions`, `item.source`, …) are a closed set, so they're just written out with the `t()`/`tr()` call the scanner already understands, the same longhand pattern `public/list.js:52` established. Plugin dimensions are an open set the kernel must never enumerate, so a plugin instead lists its own in the manifest as `facetDims: [...]` (see `plugins/jira/plugin.js`) purely so the scanner has a literal to find — this has zero effect on runtime rendering, exactly like `titleKey` already works for the tab label.

The kernel produces its own facets through the identical path, not a special one: `src/item-facets.ts`'s `kernelFacets` returns `Record<itemId, Facet[]>` for `item.agent`/`item.sessions`/`item.source`/`item.tag`, merged with whatever `collectFacets` got from plugins before the per-item cap is applied. The view layer therefore never learns, and never needs to ask, whether a chip on a card came from the kernel or from Jira. `item.agent` has exactly three values — `waiting` / `working` / `none` — and no `idle`: `idle` is this repo's pre-existing name for "sitting at the prompt, waiting on you" (`public/list.js:219`, `:258`, `:581`; `src/tmux/session-list.ts:110`), so a live session's `turn` is either `waiting` or `working` and the idle screen-marker is just the fallback used to infer `waiting` when `turn` wasn't recorded — it never produces a fourth state.

**"Sync this source" and "refresh this one item" are dispatched by the same manifest field that already carries `titleKey` and `facetDims`, not by a kernel table of plugin names.** A `Plugin` may declare `provides: string[]` (`plugins/types.ts`) — the `WorkItem.source.provider` values it claims, e.g. `["jira"]`. `plugins/handlers.ts`'s `refreshFromSource(provider, ref)` finds the one enabled plugin whose `provides` contains `provider` and calls its `refreshItem(ref)`; `runSync()` calls `sync()` on every enabled plugin that declares one and adds up the `SyncResult`s. Both live behind `src/server.ts` routes the home page calls directly — `POST /api/items/sync` and `POST /api/items/:id/refresh` — and both collapse every kind of "can't" (no source, no owner, no `refreshItem`, a throw, a timeout) into the same outcome: sync returns zeros, refresh 404s. The kernel still does not need, and is not given, a reason — that part of the design held.

What it does not license is drawing the refresh button from `item.source` alone. `/api/plugins` answers only which plugin ids are enabled, never their `provides`, so the page cannot get "does anyone claim this provider" from the kernel at all — and a button that always shows for a sourced item, with `TMUX_NEXT_DISABLE_PLUGINS` turned on for its owner, is a button that always 404s. `public/items.js` closes that gap itself: it imports the same isomorphic `plugins/registry.js` `nav.js` already uses to build the tab bar, intersects each enabled id's `provides` with `item.source.provider`, and only then offers Refresh. That is still not a kernel table of plugin names — `registry.js` is data every plugin already publishes for the browser, not a name list the kernel maintains — but it is a second, page-side decision sitting next to the kernel's single collapsed failure semantic, not a replacement for it. The 404 path still exists and still answers with one undifferentiated failure; the button is just not offered for a request the page already knows would hit it.

**`sync`/`refreshItem` get a 30-second budget (`SOURCE_TIMEOUT_MS`); `enrich` keeps its 300ms and is never expected to touch the network.** They are different jobs wearing the same "don't let a plugin hang the caller" shape. `enrich` runs on *every* page load — a facet plugin that dialled out would make the item list only as fast as the slowest tracker, so 300ms is deliberately too short for a real HTTP round trip, forcing enrichers toward cache reads. `sync` and `refreshItem` are explicit user actions — a button press, not a page load — that are *expected* to make a real request (Jira's `dev-status` plus a Bitbucket hop per PR), so the budget has to be "slow but not stuck" rather than "instant." `isConsidered`, shared by `collectFacets`, `runSync`, and `refreshFromSource`, is the one place `TMUX_NEXT_DISABLE_PLUGINS` gets checked for all three — `refreshFromSource` in particular calls `refreshItem` directly, bypassing the `/api/<id>` 404 gate that would otherwise stop a disabled plugin from running, so this filter is its only gate.

**`startPlugins()` is called from `src/index.ts`, never from `startServer()`, and `src/plugin-start-placement.test.ts` pins that split.** A dozen-plus test files call `startServer()` directly with no env overrides, the same way `migrateJiraBindings()` had to move out of `startServer()` first (see below) — a hook there would make every `bun test` run fire real plugin `start()`s against whichever credentials and `~/.tmux-next/` happen to be on the developer's machine. `startPlugins()` is synchronous and unawaited by design: the CLI entry point does not block server startup on a plugin's opening move, and a plugin that wants to do something async on boot (Jira's start-of-process sync) fires it off inside its own `start()` without kernel help.

**The provider contract (`provides`) was rejected once, then built anyway — the reversal was a new requirement surfacing, not a change of taste.** The first design had one operation (refresh) triggered only from the plugin's own page, where the plugin already knows it's Jira and can call the kernel's `ensureItemForSource`/`refreshIssue` directly — a manifest-level contract for a single call site was speculative generality, so it was cut. That stopped being true once the *kernel's* item list — a page that must not name any plugin — needed its own "refresh this item" button: at that point there is no call site left that is allowed to know it's talking to Jira, so the dispatch has to be table-driven, and the table has to be declared by the plugin (same move as `titleKey`) rather than hard-coded in the kernel. One objection raised against the original design does not survive re-examination and is recorded here so it isn't relitigated: "the plugin calling into the kernel inverts the dependency" was wrong on the facts — `plugins/jira/server.ts` already imports `src/items.ts` and `src/session-binding.ts`, so plugin → kernel was already the established direction, and `provides` does not change it; the kernel still only imports from `plugins/handlers.ts`'s static table, never the reverse.

**The home page is the work-item list now; the session list moved to `sessions.html`.** `/` serves `public/index.html`, which mounts `public/items.js` — one card per item, its facet chips, and the sessions bound to it — and `public/nav.js` builds the tab bar with `items` first and `sessions` (→ `sessions.html`) second. Places that navigate by *computing* a target were repointed: `terminal.js`'s `backPages` table (`public/terminal.js:57`) now lists `sessions.html` as its `sessions` entry, so `back-target.js` — which exists precisely so a page can return you to where you actually came from — still lands on the session list from the terminal. `public/new.html`'s back link was **not** touched, and could not need to be: it is a static `<a href="./" ...>` (`public/new.html:22`), nothing rewrites it at runtime, and it has always been an approximation rather than a real "back" — pressing ＋ from the artefacts or notifications page already returned you to the session list, not to wherever you actually came from. What this phase changed is what that approximation now points at: `"./"` used to mean the session list and now means the item list. That is a change in meaning under an unchanged link, not a regression this phase introduced, and the new-session flow is getting rewritten in the next phase anyway, so it's recorded here rather than fixed now. Grouping and filtering for the item list is a separate, `@ts-check`ed, headlessly-tested module (`public/facet-view.js`) rather than logic folded into `items.js` itself — page files aren't type-checked, and this is the one place in the item list with real branching, the kind of code where a null-handling bug silently blanks the whole page rather than failing loud.

**Work items ("单") are a kernel concept, and the binding between a session and one lives in the kernel too** (`src/items.ts`, `src/session-binding.ts`), not behind a plugin's `annotate`. An item is the unit of work; a session is one of possibly several means to it. `source` is `null` for a local item or `{ provider, ref, url? }` for one backed by an external tracker — Jira is one `provider` value, not a special case, so a local item and a claimed Jira issue are the same row on the session list. Bindings are keyed by **session name**, not item id: one item can have several sessions (a local one and a Jira-claimed one, or two panes on the same issue), so a session → item map is a single lookup while the reverse would mean scanning an array on every rename or death. Each binding record stores both the session name and its tmux `#{session_id}`, for the same reason the kernel doesn't otherwise track renames: the id survives a rename but is reshuffled when the tmux server restarts, and the name is the other way round. `resolveBindings` tries the id first and falls back to the name, migrating the record to the session's current name when the id hits — that is what lets `src/binding.integration.test.ts` rename a live session under a bound tmux session and still find it. This is also why the kernel's own `LIST_FORMAT` (`src/tmux/session-list.ts`) now queries `#{session_id}`, reversing an older rule in this file that said not to add it "for one plugin's benefit": that rule was about not distorting the kernel's session-list format to serve a private need of the Jira plugin's own `bindings.json`. Once bindings became a kernel concept, resolving them needs `#{session_id}` for the kernel's own purposes — the field belongs to the kernel now, not to a plugin, so the objection the old rule was guarding against no longer applies. The plugin-owned `plugins/jira/bindings.ts` and `plugins/jira/sessions.ts` that used to carry this are deleted; `plugins/jira/bindings-shim.test.ts` is what is left of that seam — a thin translation from the kernel's `itemId` to the Jira page's issue key, kept as a single writer for that fact rather than let the two pages disagree about a session's binding. `src/migrate-items.ts`'s `migrateJiraBindings()` runs once, from `src/index.ts` before `startServer` (not inside it — a test file that calls `startServer` without env overrides must not accidentally trip a real user's one-time migration), and moves the old `plugins/jira/bindings.json` into `items.json` + `bindings.json` without deleting the source file, so a bad migration still has something to compare against.

**A work item has no `cwd`, and re-adding one is the mistake to avoid.** It had one from phase 1 until it was removed: across 47 live items exactly one carried a value, and that one was written by a probe minutes earlier — the field was never populated in real use, so the `item.cwd` facet it fed had never once rendered. The reason it was never populated is the reason not to bring it back: an item is the *unit of work* and a directory is a property of the *means*. One issue can span two repos, or change no code at all, while a session already carries its own `path` — which is the honest answer to "where is this happening". Nothing else consumed the field: it was never passed to the new-session flow (`new.html` picks its own directory and the post-create `bind` call does not write one back), so the two "directories" were always independent. Old rows on disk may still carry `cwd`; `readItems` drops it on read and any write rewrites without it, so no migration was needed. If "which project is this item about" is wanted again, derive it from the bound sessions' paths — that is data the kernel already has and that stays true when the answer is "two repos".

**Colour themes**: every colour value lives in `public/themes.js` — seven presets (four dark, three light) × the 23 `ITheme` fields — and nowhere else. `theme-apply.js` writes two groups onto `:root`. `themeVars()` emits the `--term-*` palette, which `terminal.js` also builds its xterm theme from, so the terminal and the page cannot drift apart. `uiVars()` emits the page chrome's **role tokens**, derived from that same theme. The chosen names are stored per machine (`~/.tmux-next/theme.json`) while font size stays per device in `localStorage` — "what this machine looks like" and "how big this screen is" are separate concerns.

**Two names, because the canvas and the shell are different surfaces.** `theme.json` holds `name` (the terminal palette, feeding `themeVars`/`xtermTheme`) and `ui` (the page chrome, feeding `uiVars`); `applyTheme(name, ui)` is the only place they meet. The derivation did not change — `uiVars(ui)` emits exactly the set of values it emitted before — so the 49 combinations introduce no colour that `themes.test.ts` cannot already see, which is what made this a change of *sourcing* rather than of palette. The terminal page's own header and key bar follow `ui`, not `name`: they are chrome. So does `color-scheme`, which decides native scrollbars and `<select>` popovers, and so does the generated `manifest.webmanifest` — a splash screen is the shell.

**`ui` falls back to `name`, and that is the whole migration.** A file written before this change has only `name`, so `readTheme` resolves `ui` to it and an upgraded machine looks identical; there is no `migrate-*` step and none is wanted. The same rule is duplicated in exactly two other places for the same reason: `localStorage`'s `uiTheme` falls back to `termTheme` (a device that has loaded the app before must not flash the default on its next load), and `applyTheme(name)` with one argument paints both from it. `writeTheme` takes a **patch** and merges it against the *raw* file rather than against `readTheme()`'s resolved answer — merging against the resolved answer freezes `ui` to the default the first time someone picks a terminal palette on a fresh machine, which is the one bug in this area a test had to be written for.

The role tokens follow [Radix Colors' 12-step semantics](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale): `--surface-1..5` (app background, sunken, card, raised/hover, pressed), `--border-1..2` (divider, interactive), `--accent` / `--accent-hover` (solid fills) alongside `--accent-text` / `--accent-alt-text` (the same hues held to a *text* floor, which is a different requirement), `--text-1..3`, and `--ok` / `--warn` / `--danger`. The stylesheets consume only these; `--term-*` is the terminal's business.

**They are computed to clear their contrast floor, not hand-picked to look about right, and that is the whole point.** The chrome used to be `--card: color-mix(--term-bg 88%, --term-fg)` and `--raised` mixed again from that, with secondary text taken from the theme's ANSI bright-black slot. Every contrast assertion in `themes.test.ts` measured against the *terminal* background, and a `color-mix()` resolves in the browser — so the page's own surfaces had no coverage at all. Measured after the fact: secondary text sat at 2.63–3.30:1 on a card and **1.89–2.35:1 on a chip**, across all four themes, and that colour draws the status, the timestamp, the facet labels and every button label on a card. `dimTo()` now walks the foreground toward the surface and stops at the last step still clearing 4.5:1; `liftTo()` lifts a too-dark semantic colour toward the theme's own bright white until it clears 3:1 (Nord's red for "End session" was 2.24:1). The floors are met by construction, and `themes.test.ts` measures every role token on `--surface-4` — the lightest surface in common use, so the worst case for light text.

Because the roles replaced what the stylesheet had been hand-mixing, the colour-literal exemption list in `themes.test.ts` went from 22 entries to 4. What is left is genuinely not themeable: the white background of the gallery's artifact `iframe` (someone else's HTML, which assumes paper), and three black scrims and a shadow — a scrim is black by definition. That list only shrinks.

`src/themes.test.ts` still enforces WCAG AA on the terminal palettes too; the thresholds are AA, not AAA, because two of the four upstream themes cannot clear AAA.

**Light themes are more presets, not a second axis.** They added no field: `theme.json` stored one name then, and the second name it stores now is the terminal/chrome split above, not a polarity switch. A theme's polarity is *computed* — `isLight(t)` is `luminance(background) > luminance(foreground)` — rather than declared, so a `dark: true` field can never disagree with the colours it describes. Everything in `uiVars()` that pushes a colour "until it clears the floor" takes its endpoint from that: `#ffffff` for a dark theme, `#000000` for a light one. Writing the endpoint as the theme's own `ansi[15]` is what the code used to do, and it fails in both directions — on a light theme the surfaces are already near white, so pushing toward white walks off the end of the loop and returns the endpoint itself (Latte's `--ok` and `--warn` both became `#bcc0cc`, 1.30:1 on a card); and even on a dark theme it is too weak for `--accent-hover`, because Catppuccin Mocha's bright white and its blue are only 1.057 apart. There is no Nord light: on a Snow Storm background its yellow lands at 1.35:1, its cyan at 1.74:1 and its green at 1.77:1, so a "Nord Light" would be a new palette wearing the name, with no upstream to check it against. The picker is deliberately asymmetric — four dark, three light — rather than inventing one.

**Two weaknesses in the accent roles are known, measured, and deliberately not fixed here.** `--accent` is a solid fill, so WCAG 1.4.11 asks 3:1 against what it sits on, and nothing asserts that: Tokyo Night Day reaches only 2.93:1 on `--surface-4` and 2.72:1 on `--surface-5`. This is not something the light themes introduced — Nord has sat at 3.20:1 and 2.83:1 since the role tokens landed — but Tokyo Night Day is now the worst case, and the dimension has no test at all. Separately, `--accent-text` is derived by pushing the theme's blue toward the foreground, which collapses when the foreground is itself blue: on Tokyo Night Day it lands 1.076 from `--text-1`, so a link and body copy are the same colour to the eye (One Dark was already at 1.104). The same push makes `--accent-alt-text` and `--accent-text` differ by 1.02 or less in five of the seven themes, which means the comment calling it "the second distinguishable colouring" is currently writing a cheque the derivation does not cash. Both want a real fix — an accent that is checked against its surface, and a second hue chosen rather than pushed — and both are wider than adding light themes, which is why they are recorded here instead.

**Raising a surface assumes the foreground has headroom, and one theme proved it.** `--surface-2..5` are the background mixed toward the *foreground*, so every step eats contrast that `--text-1` needs. The four dark themes hide this: their foregrounds are near-white, 8–11:1 on their own backgrounds. Tokyo Night Day's upstream foreground is a mid-tone blue at 4.52:1 — no headroom at all — and `--text-1` fell to 3.54:1 by `--surface-5` while `dimTo` could not move `--text-2` a single step. The fix is in the data (darken the foreground 18% to `#2d4f9d`), not in the surface ramp, because the ramp is what every other theme depends on. `%s: 表面层级单调远离底色` is the assertion that keeps the ramp honest in both polarities: "raised" means lighter on a dark theme and darker on a light one, and getting it backwards would leave every contrast assertion green while the `--surface-4` baseline they all measure against became the wrong end of the scale.

**One computed token drifted, and the lesson is the missing test rather than the colour.** Switching the semantic colours' endpoint from the theme's own `ansi[15]` to a polarity-chosen pure black or white moved exactly one value across the four dark themes: Nord's `--danger`, from `#cb868e` to `#ce878e` (3.0142:1 to 3.0720:1 on a card — better, and imperceptible). It is the only one of the twelve dark semantic slots whose starting colour does not already clear `MARK_FLOOR` on `--surface-4`, so it is the only one where `pushTo` actually interpolates and the endpoint matters; the other eleven return their starting colour untouched and would look identical against any endpoint. The design had written "the dark themes are unchanged byte for byte" on the strength of those eleven — a coincidence mistaken for a rule. What made it a defect worth recording is that **nothing in the suite could have caught it**: every assertion here measures a contrast ratio, and a ratio that moves from 3.01 to 3.07 still passes. `%s: 深色主题的角色令牌逐键钉住` is the test added in response — it pins all four dark themes' `uiVars()` output key by key, so the next change to how a token is derived has to state out loud that it is changing what those themes render. The light themes are deliberately excluded from that pin while they are still being built. When the list goes red, the question to ask first is "was this change supposed to alter colours?", not "what are the new values?".

**Responsive layout is two orthogonal questions, never one "is this desktop" switch.** `@media (min-width: 900px)` decides layout — content column, card grid, sheet centred instead of bottom-anchored. `@media (hover: hover) and (pointer: fine)` decides interaction — hover states, and whether the terminal's soft-key bar comes pre-expanded. Merging them breaks real devices in both directions: an iPad in landscape is wide but has no mouse, so binding the key bar to width takes Esc / Tab / arrows away from the device that needs them most; a half-width window on a Mac has a mouse but is narrow, so binding hover to width makes pointer feedback vanish. `pointer: fine` is not optional in that second query — a touchscreen Windows laptop reports `hover: hover` too. There is no UA sniffing and no second set of pages; the whole thing is media queries at the end of each stylesheet, and every narrow-screen rule is untouched.

900px is the only width breakpoint in the codebase, and `src/responsive.test.ts` is what keeps it that way. CSS `@media` cannot read a custom property, so the literal is written once per stylesheet — kernel plus every plugin — with nothing stopping the next person writing 768px in one of them. Three files switching at three widths produces a bug that exists only inside one band of window sizes, which is why the test scans all of them (the same shape as `themes.test.ts`'s colour-literal scan) and also rejects any single `@media` that mentions both a width and a pointer. It carries one more guard that is not about responsiveness at all: the kernel stylesheet must not name a plugin. That rule nearly broke here — the wide-screen grid clears each card's margin, work-item cards are `.item-card` but Jira's are `.jira-card`, and adding that one selector to `public/style.css` would have made a kernel rule depend on a directory that `TMUX_NEXT_DISABLE_PLUGINS` can switch off. The grid for `#issues` lives in the Jira plugin's own stylesheet instead.

**A session card has two action entry points, and CSS — not JavaScript — decides which one you see.** `list.js` always builds both: the `⋯` button that opens the action sheet, and a `.card-actions` row along the bottom of the card. The stylesheet shows the row and hides `⋯` above 900px, and the reverse below it. Reading `matchMedia` in JS instead would mean owning resize handling and re-render timing for a decision that has no state behind it. The three behaviours (`pinSession`, `pickItemFor`, `confirmAndKill`) are named functions both entry points call — they were inline in `openActions` until the row existed, and two copies of "toggle the pin" would have drifted with nothing going red, since each entry point still works on its own while doing something different. `src/list-page.test.ts` asserts the row's labels, that `⋯` survives alongside it, and that both paths POST to the same endpoint; removing `⋯` from the card turns eight tests red, which is the point — deleting it looks fine on a desktop and silently removes every action on a phone.

Ending a session sits apart in that row: `margin-left: auto` and the theme's red. The old `⋯` button was deliberately small and off in a corner because "ending a session is destructive, so it should take aim rather than sit under a thumb" — surfacing the action as a full-size button next to Pin would have thrown that away. It still raises a confirmation sheet, so the separation is about not steering the hand there, not about being the last gate.

**The item list has a second layout — a table — and its columns come from the filter fields, not from the data's dimensions.** `public/items.js` renders either cards or a table from the same `filtered` array, chosen by `tmux-next.items.view` (`"cards"` default; anything unrecognised falls back to cards, the same shape as the other four device-local keys). Grouping, filtering and the work filter mean exactly the same thing in both, so switching never loses context: the group name becomes a `colspan` heading row inside the table rather than each group starting its own table, because a per-group table repeats the header and the columns then stop lining up down the page — and lining up is the entire reason to pick the table. Every part is the card's part (`itemSource`, `facetChip`, `sessionRow`, `itemActions`, `newSessionLink`); two implementations of "when is a chip clickable" would drift with nothing going red, since each view still looks right on its own while saying something different. `itemSource` and `newSessionLink` were extracted out of `itemCard` for exactly that reason.

The columns are the fixed three (item, `item.agent`, `item.sessions`) plus **one per field already added to the filter area**, and `public/item-table.js` is where that is decided — `@ts-check`ed and headlessly tested, like `facet-view.js`, because a wrong answer here is silent (a column of empty cells, or a dimension quietly dropped). Dimensions are an open set, so spreading all of them would make the width a function of how many plugins are installed; which ones are worth a column is a judgement the user already made once via 「添加字段」, and reusing it means no second switch to learn. `tableColumns` drops the two dimensions that already have fixed columns, so adding `item.agent` as a filter field cannot produce the same column twice, and `facetsIn` returns *every* facet of a dimension — one dimension can hold several values (tags do), and painting only the first would drop data inside a layout whose whole promise is that you can see the field.

The view selector is not drawn below 900px (`.view-mode-wrap`), so a phone can never store `table`: a table on a phone is a horizontal scroll through the one thing you wanted to scan. A desktop window dragged narrower keeps whatever it stored, and `.table-wrap` degrades that into a scroll instead of breaking the page. That is a CSS decision, not a `matchMedia` read, for the same reason the session card's two action entry points are.

**Cards in the grid are the same size, and the two lists get there differently.** Both use `align-items: stretch` with the action row pushed down by `margin-top: auto`, so a row of cards shares a bottom edge and the buttons line up. Session cards go further and fix their height (288px), because their body is a terminal preview whose length is whatever happened to be on screen — one card running `npm install` would otherwise stretch its whole row to half a viewport. That truncation is safe precisely there: the preview is already a truncated screenful, and the card clips it under a `mask-image` fade so it reads as "there is more" rather than as the end. Work-item cards are *not* fixed-height, because their body is a list of bound sessions and every row in it is a link — clipping those hides functionality rather than log spill.

A grid-placed card needs `min-width: 0` and `overflow: hidden`, and both are load-bearing. A grid item defaults to `min-width: auto`, so a card holding a `white-space: nowrap` row (session state, relative time, the short sha) widens its whole track; without the clip, the overflow paints across the neighbouring card rather than off the screen edge the way it does in a single column. Clipping alone then truncates the very thing the row exists to say — "waiting 5m" became "wait" — so on wide screens `.name-row` / `.meta-row` wrap and `.item-title` stops ellipsizing. Narrow stays as it was: one screen is short, and a three-line title there pushes every other card below the fold.

The desktop two-pane layout — list on the left, terminal on the right, in the shape Tembo uses — is deliberately **not** built. It needs `terminal.js` to stop being a page and start being a component: it reads `location.search`, writes `document.title`, binds the keyboard globally, and owns `--app-height`. That is a runtime refactor, and this layer is styling only. See `docs/superpowers/specs/2026-09-02-responsive-desktop-design.md` §5 for the couplings to unpick.

**Claude Code integration**: `bunx tmux-next hook` (`src/hook-setup.ts`) installs two scripts into `~/.claude/hooks/` and registers `SessionStart` (records `{name,id,cwd}` for restore) plus `Stop`/`SessionEnd`/`Notification` (POST to `/api/notify` → Web Push). Both scripts resolve their tmux session with `list-panes -a` filtered against the `web-` prefix, never `display-message -t <pane> '#{session_name}'` — a pane belongs to every session grouped onto its window, and that form collapses the set to the most recently created, which is always tmux-next's own mount point while a browser is watching. Using it made both hooks silently no-op on exactly the sessions someone had open (`src/hooks.test.ts` covers this). Hook registration is idempotent, backs up `settings.json`, and never clobbers existing config. `src/web-push.ts` hand-rolls VAPID (RFC 8292) and aes128gcm payload encryption (RFC 8291/8188) on WebCrypto, so the package keeps zero server-side runtime dependencies.

## Conventions that matter

**Every tmux call goes through `tmux(argv)` in `src/tmux/run.ts` — never `Bun.$`.** The shell applies word splitting to interpolated values in an environment-dependent way; under launchd a tab inside a `-F` format was rewritten to `_` and corrupted every parsed field while working fine interactively. `run.ts` also forces `LANG`/`LC_CTYPE` to UTF-8 or tmux mangles CJK in `capture-pane` and `send-keys`.

**Target tmux by `=<name>`, always.** A bare target resolves by prefix and glob — `kill-session -t web` would kill `webmux`.

**Never run `tmux kill-server`, and never kill a tmux session you did not create.** The tmux server owns every pane's PTY and child process on the machine, so killing it destroys every running session at once — including the user's work, which no test needs to touch. Clean up only by exact name (`kill-session -t =<name>`) against names the current run created and recorded.

This is not hypothetical. A run once tried to re-check the orphan-session tests under an isolated server:

```bash
export TMUX_TMPDIR=$(mktemp -d)   # intended to isolate
bun test ...                      # output showed 12 sessions, not 1
tmux kill-server                  # ran anyway — killed the real server
```

The isolation silently failed, and the evidence that it had failed was already on screen — a count that could only come from the real server. Twenty-six sessions and thirty-two Claude processes died. Three could not be restored, because a separate bug had left them without binding records.

The rule that would have prevented it: **a destructive command must be preceded by a check that its target is what you think it is, and that check must be read before the command runs.** Verifying afterwards is not verifying. When an isolation premise cannot be confirmed, the destructive step is cancelled, not attempted.

**A test that creates a session with `-c <dir>` must not delete that directory while the tmux server is still alive.** During this phase's integration run, a test created a session with `-c` pointing at a temp directory, then cleaned that directory up afterward as normal test hygiene — but the tmux *server* itself had adopted that path as a stored working directory, not just the one pane. Every pane created afterward, in any session, inherited the now-deleted cwd: `/bin/pwd` fails with `.: No such file or directory` even when the new pane is given an explicit `-c` of its own, so the login shell can't start and anything launched in it dies immediately. This is not scoped to the session the test created — it wedges the whole shared server. On a developer machine that server is long-lived and holds real work sitting alongside whatever the test suite is doing; there is no clean fix once it happens short of restarting the server, and restarting it destroys every session on the machine, which is exactly the operation this file already says never to do casually (see above). The suite in this repo currently carries a stable 9-failure/1-error tail attributable to this — it is a known, load-bearing scar, not a flaky count to chase down by rerunning. Nothing here proposes a fix or a test change; recording the mechanism is the point, so the next person who hits `pwd` failing inside an otherwise-healthy pane recognizes it instead of debugging the wrong layer.

**Confirm what a running process is actually serving; do not infer it from timestamps.** `public/` is read from disk per request (`Bun.file(PUBLIC_DIR + name)`), while `src/` is loaded once at startup and Bun does not reload without `--watch`. So after an edit the front-end is live immediately and the back-end is not — a running server is routinely half-new, and "started before the commit" proves nothing about what it serves. Check the endpoint or asset itself.

**Nothing from a request is spliced into a shell command.** The launch command is one of two fixed constants (`LAUNCH_COMMAND` / `LAUNCH_COMMAND_SKIP_PERMISSIONS`); the directory travels as its own argv via `-c`; a resume id must match `/^[A-Za-z0-9-]{1,64}$/` or the request is rejected. Untrusted geometry goes through `sanitiseGeometry` before reaching tmux — that is why the `ClientMessage` dimensions are typed `unknown`.

**There is no auth and no directory allow-list, on purpose.** Anyone who reaches the interface can already attach to a session and type `ls`; fencing the file browser would only be theatre while costing machine-specific paths in the source. The service binds loopback and assumes a reverse proxy for TLS + auth. Do not add features that assume the server is safely exposed. `/api/notify` is loopback-only because the server *may* be bound wider.

**Commit messages carry no assistant attribution.** No `Co-Authored-By: Claude …`, no `Claude-Session:` line, no `🤖 Generated with …` footer — regardless of any default that would otherwise append them. The repository is public and these trailers surface as an extra contributor on every commit; the history was scrubbed once to remove them and must not reacquire them. Describing Claude Code in the *body* is fine and often necessary — this project exists to watch it — the rule is about attribution trailers, not the product name.

**Every on-disk state path is env-overridable** so tests never touch the user's `~/.tmux-next/`: `TMUX_NEXT_SESSIONS_DIR`, `TMUX_NEXT_GALLERY_DIR`, `TMUX_NEXT_KEY_USAGE_PATH`, `TMUX_NEXT_PINS_PATH`, `TMUX_NEXT_VAPID_PATH`, `TMUX_NEXT_PUSH_DIR`, `TMUX_NEXT_NOTIFICATIONS_PATH`, `TMUX_NEXT_THEME_PATH`, `TMUX_NEXT_ASR_PATH`, `TMUX_NEXT_ITEMS_PATH`, `TMUX_NEXT_BINDINGS_PATH`, `CLAUDE_PROJECTS_DIR`. The notify hook also honours `TMUX_NEXT_HOOK_LOG` (a path, or `off`). Paths are read lazily inside functions, not captured at module load, so a test can set the env var before the first call. New state must follow this pattern.

**A browser module that renders must have a test that renders it.** `public-parses.test.ts` proves a file parses and `Bun.build` resolves its imports; neither proves it draws anything. Two bugs shipped through that gap — `tr` called 25 times with no import (valid JavaScript, dies at runtime), and a `history.replaceState` throw in the middle of `browse()` that skipped the directory list, breadcrumb and favourites. `src/new-page.test.ts` mounts the page in happy-dom and asserts on the DOM; anything with comparable rendering logic needs the same. A DOM shim must restore the globals it replaces — overwriting `fetch` once broke 38 tests in other files, since Bun runs them in one process.

**Session "last updated" comes from content diffing, not tmux.** `session_activity` only advances while a client is attached (frozen for the detached sessions this app lists); `window_activity` advances on any repaint, so every live Claude session reads "just now". `window_activity` seeds a session first seen this process, then `activity-stamp.ts` stamps on actual `capture-pane` content changes.

## Testing

~300 tests, most of which really drive tmux — creating sessions, sending keys, reading back formats like `#{pane_start_command}` to prove the arguments landed. Tests clean up their own sessions in `afterEach`/`afterAll`. Files named `*.integration.test.ts` are the heaviest of these.

Pure logic (paths, geometry, gesture translation, control-protocol parsing, Web Push crypto) lives in DOM-free modules tested on their own.

`src/hooks.test.ts` drives the two shell hooks against a real tmux server, including the grouped-session case — Claude spawns those scripts, so nothing else in the suite would catch a regression there.

`src/public-parses.test.ts` bundles every file in `public/` with `Bun.build` — those files are loaded only by a browser, so a syntax error there ships silently and the suite stays green. It exists because that happened twice.

**Orphan-session assertions are scoped by pid, and must stay that way.** The tmux server is shared with everything else on the machine — very often a real tmux-next serving someone's phone, whose sessions are just as legitimately named `web-…`. `server.test.ts` and `reconnect.test.ts` therefore filter on `web-${process.pid}-`, not on `web-`. They used to count every web session on the box, which made them fail permanently on any machine where the app was actually in use, and that failure was written off for a long time as parallel-run flakiness. It was not: it reproduced with the file run alone. The pid in the name (`web-<pid>-<random>`, `session-manager.ts`) is what makes orphan collection decidable from outside the process, and it is what makes "did *I* leak one?" answerable in a test.
