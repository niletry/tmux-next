# 无头会话 API 设计

2026-09-17

## 背景

tmux-next 现在是一个自带 UI 的服务：`public/` 里的页面和 `src/` 里的路由一起发布，
接口的形状是按页面需要长出来的。目标是让它变成一个稳定的幕后提供者——第二个前端
（手机原生端、桌面端、CLI）能完整管理本机的 tmux 会话，内置 Web UI 降级成这套接口的
第一个客户端。

「管理」在这里的含义是具体的：列举会话、知道每个会话此刻在等人还是在干活、向其中一个
打字、起新的、杀掉旧的、以及在状态变化时被**通知到**而不是靠轮询发现。今天这套接口
能做前面几件，最后一件完全做不到——全仓库没有一处 `text/event-stream`，唯一的长连接
`/ws` 只搬一个 pane 的原始字节。监察者插件靠 `/loop` 自己掐表、自己去磁盘读别的会话的
transcript，正是因为没有一条流可订。

## 范围

**在范围内**：会话资源、agent 目录、事件流、Webhook、终端 WebSocket 契约、写操作的
幂等与批量、能力协商。

**明确不在范围内**：工单（单）、绑定、facet、来源插件那一整套。它们留在 `/api/items/*`，
内置 UI 继续使用，但不进对外契约。这是一次范围收敛的结果，不是遗漏。

**明确不做**：URL 版本号（见「能力协商」一节的理由）、服务内置鉴权（见「鉴权与暴露面」）、
持久化的事件历史（见「事件流」的重连语义）。

## 四个已定的前提

1. **一套契约，内置前端做它的第一个客户端。** 不新设 `/api/v1/*` 平行接口。两套路由
   描述同一批东西必然漂移，而这个仓库对这种形状的教训写得最密：卡片渲染提取成共享
   模块的理由就是「同一个 chip 画两遍最终会说两种话」，插件的两张表必须靠测试强制同步。
   两套 API 是这个错误的最大号。代价是 `public/` 要改，收益是只有一套真相，而且前端
   吃自己的狗粮是「接口够不够用」唯一可靠的检验。

2. **用能力协商代替版本号。** 调用方是自己的第二个前端，真正会发生的不一致不是「第三方
   没跟上」，而是手机上的 App 版本和机器上跑的 tmux-next 版本对不上——服务端是 npm 包
   由用户自己升级，客户端要过应用商店审核。`/api/v1` 解决不了这个。`GET /api/capabilities`
   让新客户端连到老服务器时自己降级，而不是撞上 404 再猜原因。

3. **终端是公开契约的一部分。** 第二个前端是完整替代品，自己接 WebSocket、自己跑终端
   渲染器。

4. **事件流是地基，Webhook 是它上面的一个转发器。** 一套事件定义，两种投递方式，不会
   出现两边说法不一致。

## 稳定性承诺从哪一刻开始

「非常稳定的幕后提供者」是这件事的**首要目标**，但分期本身是一串破坏性变更：`/keys`
换含义、`preview` 默认值翻转、`/api/local/*` 搬家。如果不说清承诺何时生效，「稳定」
就只是一句愿望。

- **第 1 到 5 期是明确的 pre-1.0。** 这期间接口会变，第二个前端跟着主干走，不保证兼容。
- **第 5 期结束时冻结契约。** 冻结之后，字段只增不减、不改含义；要废弃一个东西，先加
  新的、让两者并存一个发布周期、再删。
- **执行手段有两个，都不是靠自觉。** `/api/capabilities` 让客户端能发现自己面对的是
  哪一档服务器；契约快照测试把对外字段集钉成 fixture，改了就红——目的不是禁止改，是
  逼着每次改动说出口（见「测试策略」）。

在冻结之前，每一期的破坏性变更都要在发布说明里逐条列出。这是唯一能让「稳定」从形容词
变成可检查的东西的做法。

## 契约边界

对外只有两类资源。

- **session**：一个 tmux 会话连同跑在里面的 agent。唯一有生命周期和输入输出的资源。
- **agent**：只读目录，回答「这台机器能起什么」，每项带自己的能力位（只有 Claude Code
  有跳过权限模式）。

边界线是 `/api/local/*`：`theme`、`language`、`asr`、`key-usage` 挪进这个命名空间，明确
声明不在契约内。它们是内置 Web UI 的偏好，第二个前端有自己的主题和语言。用命名空间而
不是文档里一句「这几个不算数」，是因为结构能自我执行，文档里的规矩可以被绕过——这条
理由在本仓库已经用过一次，就是插件 legacyPaths 的重定向刻意排在静态文件查找**之后**。

`/api/items/*` 保持原样，不动，不承诺。

## 会话资源

沿用现有的 `SessionSummary`（`src/tmux/session-list.ts`），改三处。

### 1. 预览改成显式索取

`preview` 和 `pendingInput` 改成 `?include=preview` 才回传。

默认关而不是默认开，是因为契约的默认值应该是最小的那个，扩展要显式。代价是最主要的
消费者（会话列表页）每次都得带上这个参数，这是一次性的成本；反过来默认开的话，每个
只想要一张状态表的客户端都要一直为一屏幕文本付钱，而且它不会知道自己在付。

**截屏必须照跑。** `preview` 和 `lastActivityEpoch` 是同一次 `capture-pane` 的产物：
活动时间戳靠比对屏幕内容变化来盖，跳过截屏，「最后更新」就会退回那个对每个活跃会话
都读「刚刚」的 `window_activity`。可选的只是要不要把那四行塞进响应，不是要不要截屏。
这一条必须写在实现注释里，否则下一个做性能优化的人会把截屏一起省掉，而症状是时间戳
变钝，不会有任何测试变红。

### 2. 补单个会话的读路由

`GET /api/sessions/:name`。这个路径现在只挂了 DELETE，想查一个会话的状态必须拉整张表
再自己过滤。

**它必须排在 `/screen`、`/transcript` 这些更具体的 GET 之后。** 现有的删除路由用的是
`/^\/api\/sessions\/(.+)$/`，`.+` 会把 `foo/screen` 整个吞掉。这个仓库已经为同一类
错误留过疤——`/api/items/by-session` 必须排在 `/api/items/:id` 之前，否则 by-session
被当成 id——并且是靠断言那里返回 200 来钉住顺序，而不是靠一句注释。新增的这几条同样
要有一个断言顺序的测试。

### 3. 列表支持过滤

`?state=waiting`、`?path=`、`?agent=`。挑出「在等我的那些」是每个客户端都会重写一遍的
代码。

### 列表端点瘦身

`GET /api/sessions` 今天返回 `{sessions, items, facets}` 三样，因为首页要一次画完。
契约版本只返回会话数组，items 和 facets 改成 `?include=items,facets` 索取——和 preview
共用同一个机制。第二个前端拿到干净的资源集合，内置 UI 仍然一次请求画完首页。

`itemId` 字段保留在会话对象里，标注为契约外。分层不该让内置 UI 丢掉绑定关系。

### `idle` 与 `turn` 的消费顺序写进契约

两个字段都留着。`turn` 读的是 transcript 里的 `stop_reason`，是记录格式的一部分；
`idle` 认的是 TUI 上的空闲标记，会随 agent 改版失效。不是 Claude、或者没有绑定记录的
会话只有 `idle` 一个信息源，删掉它们在列表上就完全没有状态。

规则：**`turn` 优先，为 null 时退回 `idle`。** 这个约定现在已经在会话列表页
（`public/session-state.js`）和工单 facet（`src/items/facets.ts` 的 `stateOf`）两处收敛，
只是从没写下来。契约化就是把它写下来。

### 时间

统一 epoch 秒。会话的 `lastActivityEpoch` 和现有记录恰好都是，不用改，写进文档即可。

### 「卡住了没有」是可推导的，契约要说明怎么推

这是 agent 管理里最常被问的问题，而它不需要新字段：**`turn` 是 `working`，但
`lastActivityEpoch` 已经很久没动**，就是卡住的信号。契约要写明这两个字段可以这样合用，
以及各自的精度——`lastActivityEpoch` 盖的是**可见内容变化**的时刻，所以一个正在刷进度
条的会话会一直刷新它，而一个真的挂死的会话不会。

不把「卡了多久」做成服务端算好的字段，是因为「多久算卡住」是客户端的判断，不同场景
阈值不同。服务端给事实，客户端给判断。

### 新增两个读路由

- `GET /api/sessions/:name/screen` —— 完整屏幕，而不是四行。
- `GET /api/sessions/:name/transcript` —— 结构化轮次。监察者现在是直接去磁盘读别的
  会话的 JSONL，那是私有路径不是接口。任何想判断「这个会话卡住了没有」的客户端都需要
  它，顺带它也是 token 用量唯一的来源。

## 事件流

`GET /api/events`，SSE。

### 事件信封

一份定义，两种投递。SSE 和 Webhook 发的是同一个对象。

```json
{
  "id": "evt_01J8...",
  "type": "session.turn",
  "at": 1758067200,
  "session": "my-project",
  "data": { "turn": "waiting", "previous": "working", "sessionId": "$7" }
}
```

SSE 的 `id:` 字段镜像 `id`，`event:` 字段镜像 `type`，`data:` 是整个信封的 JSON。
Webhook 把同一个对象作为请求体 POST 出去。

### 事件类型

| type | 何时发 | data |
|---|---|---|
| `session.created` | 出现了一个没见过的会话 | `sessionId`, `path`, `agent`, `agentLabel` |
| `session.ended` | 一个会话消失了 | `sessionId` |
| `session.renamed` | `sessionId` 不变但名字变了 | `sessionId`, `previousName` |
| `session.turn` | 轮次状态变化 | `turn`, `previous`, `sessionId` |
| `session.attention` | agent 主动要人（权限询问等） | `message` |

还有一个**流控制事件** `resync`，它只走 SSE，不投递给 Webhook：它说的是「这条连接跟丢了，
你自己去重新拉一次列表」，是关于连接的事实而不是关于会话的事实。Webhook 是无状态的
单次投递，没有「跟丢」这个概念，所以给它发 `resync` 没有意义。

### 先说清楚：服务端今天没有轮询循环

这是整个设计里最容易被想当然的一点。**轮询是浏览器在做的**——`public/list.js:807` 和
`public/items.js:1334` 各自 `setInterval(…, 5000)` 去调 `/api/sessions`。服务端唯一的
定时器是 60 秒的孤儿回收，`listSessions()` 只在请求处理里被调用。

所以一个没有浏览器连着的 tmux-next 几乎什么都不做，而这恰恰是 Webhook 最该工作的时刻。
**事件流必须自带一个服务端轮询循环**，这不是既有机制的复用，是新造的东西，而且它改变
了服务在空闲时的行为。

代价是实打实的：`listSessions()` 为每个会话起一次 `capture-pane` 子进程，负载按会话数
线性增长。所以这个循环**按需启停**：

- 有至少一个 SSE 订阅者，或者注册了至少一个未停用的 Webhook → 循环跑。
- 两者都没有 → 循环停，服务回到今天的静息状态。

这样「没人关心的时候不烧 CPU」是结构性的，而不是靠调一个间隔值去平衡。附带的好处是
升级路径干净：没人用新接口的机器，行为和今天逐字节相同。

### 两个生产者，靠「状态变化才发」天然去重

- **轮询循环**覆盖所有会话，包括不是 Claude 的，代价是最多晚一个轮询间隔。
- **hook** 更快：`/api/notify` 收到 Claude Code 的回调，亚秒级，但只覆盖 Claude，而且
  只在钩子装好的机器上有。

这是**覆盖面的描述，不是职责的划分**。不需要按事件类型把权威判给谁，因为这几个事件
说的都是**状态**而不是**边沿**：总线保存每个会话的上一次已知状态（存在与否、轮次），
只在状态真的变了时发事件，谁先发现谁发。`ended` 也一样——会话离开已知集合就发一次，
hook 抢先发了，轮询再看到时状态已经变过，不会重复。

这比「hook 发过的就让轮询跳过」简单，而且没有时间窗要调。

### 重连语义

用 SSE 原生的 `Last-Event-ID`。服务端保存一个**有界**环形缓冲（内存，进程生命周期）。

- 客户端带着一个还在缓冲里的 id 重连 → 补发它之后的全部事件。
- 带着一个已经被挤掉的 id、或服务器重启过 → 发一个 `resync` 事件，客户端自己去重新
  拉一次列表。

**不做持久化的事件历史，也不假装做了。** `resync` 是诚实的答案，和这个仓库处理
`checksKnown: false` 的方式是同一个原则：「没拿到」和「没有」是两件不同的事，合并它们
会让客户端在看起来整洁的方向上说谎。

### 心跳

每 15 秒发一个 `:ping` 注释行。反代和移动网络会掐掉长时间没有字节的连接。

### 与 Web Push 的关系

Web Push 面向锁屏的手机，SSE 面向活着的客户端。两者必须由同一个事件总线喂养，否则会
对同一件事给出不同说法。

实现上这意味着一次重构：`/api/notify` 现在直接调 `notify()` 发推送，改成**发布到总线**，
总线有三个订阅者——推送发送器、SSE 扇出、Webhook 派发器。总线本身是一个 DOM-free 的叶子
模块（`src/events/bus.ts`），`publish` / `subscribe` 两个函数，可以脱离服务器纯逻辑测试。

## Webhook

### 订阅管理

`GET` / `POST /api/webhooks`，`GET` / `DELETE /api/webhooks/:id`。

存储在 `~/.tmux-next/webhooks.json`，通过 `TMUX_NEXT_WEBHOOKS_PATH` 覆盖，路径在函数
内部惰性读取而不是模块加载时捕获——这是本仓库既有的约定，测试才能在第一次调用前设好
环境变量。

记录形状：`{ id, url, events: string[], secret, createdAt, disabled, lastError }`。
`events` 为空数组表示订阅全部。

### 签名

`X-TmuxNext-Signature: t=<epoch>,v1=<hex>`，HMAC-SHA256 覆盖 `<t>.<body>`。用 WebCrypto
手写，零运行时依赖——和 `src/web-push.ts` 手写 VAPID 与 aes128gcm 是同一个取舍。

时间戳进签名是为了让接收方能拒绝重放。

### 投递与失败

- 单次投递超时 5 秒。慢的接收方不能把总线堵住。
- 失败重试 3 次，退避 1s / 5s / 25s，然后放弃并写进 `lastError`。
- **至少一次投递。** 每个事件带稳定的 `id`，接收方自己去重。
- **信封里加一个单调递增的 `seq`。** `id` 只能让接收方发现*重复*，发现不了*缺口*——
  重试耗尽、订阅被自动停用，事件就是真的没送到，而接收方对此一无所知。`seq` 跳号就是
  缺口，接收方据此自己去拉一次列表对账。这是 Webhook 侧对应 SSE 那个 `resync` 的东西，
  只是由接收方自己判断而不是由服务端告知。
- 连续失败 20 次自动置 `disabled: true`，不再投递。一个已经死掉的 URL 不该被无限期地
  敲下去，而且这个状态要能在内置 UI 上看见。

**不做持久化投递队列。** 进程重启后在途的重试就没了。理由和事件历史一样：一个诚实的
「没送到」比一个假装可靠的队列好，真需要可靠投递的接收方应该自己对账，而它已经有
`resync` 和列表接口可以对。

## 终端契约

把现有 `/ws` 的语义写死，补两个缺失的控制帧。

### 分帧规则

已经是对的，只是没写下来：

- **二进制帧 = pane 输出字节。**
- **文本帧 = JSON 控制消息。**

客户端侧靠 `event.data instanceof ArrayBuffer` 区分。

### 客户端 → 服务端

- `{t:"open", target, rows, cols}` —— 打开一个会话。**会先关掉这个 socket 上已有的
  会话**，一个 socket 同时只挂一个。
- `{t:"keys", hex}` —— 空格分隔的十六进制字节。
- `{t:"resize", rows, cols}`

### 服务端 → 客户端

- 二进制帧 —— pane 输出。
- `{t:"error", message}` —— 已有。
- `{t:"ready", cols, rows}` —— **新增**。`open` 成功后发，带上 tmux 实际定下来的尺寸，
  而不是客户端请求的尺寸。
- `{t:"exit", reason}` —— **新增**。今天 `onExit` 直接 `ws.close()`，客户端分不清
  「会话死了」和「网断了」，重连循环只能盲目重建。

### 几何

`sanitiseGeometry` 的边界进文档：cols 20–1000（缺省 80），rows 5–500（缺省 24）。
**越界是钳制，缺失是回落到缺省**，两者不同——客户端省略一个维度是在说「没有偏好」，
把它钳到 `min` 会给每个旧客户端一个 20 列的窗口，这是真实发生过的 bug。

### seed 语义

契约必须写明：`open` 之后服务端发的第一批字节是一个 seed，它同时还原**内容和终端模式**。
`capture-pane` 只给文本，seed 里的 `\x1b[2J\x1b[H` 会清掉模式，所以还要重放鼠标跟踪的
DECSET（由 tmux 的 `#{mouse_*_flag}` 驱动）。**客户端收到 seed 之后不得再自行清屏。**

这一条是整个终端契约里最容易被下一次重构弄丢的东西，而症状是「用鼠标的程序回来之后
滚轮失效」，没有任何测试会红。

### 一个 socket 一个一次性会话

每个 socket 打开时创建 `web-<pid>-<random>` 分组会话，关闭时销毁并跑 `resize-window -A`
把尺寸交还给其余客户端。

**契约要写明的副作用**：窗口尺寸是分组共享的，所以同一个目标上的两个客户端会互相抢
尺寸。

这一条不能只当作「已知行为」记一笔。它今天是个偶发问题（同一个浏览器的后台标签页偶尔
踩到，症状是输入框消失），而**把多客户端写进契约会让它从偶发变成必然**：手机和笔记本
同时开着同一个会话是这套接口最正常不过的用法。一个号称稳定的提供者，不能在最正常的
用法上交出一个抖动的窗口。

所以这是冻结契约**之前**必须有答案的问题，而不是一条告知。可选方向有两个，都还没定：
让每个 socket 声明自己是否参与尺寸协商（只读观察者不参与），或者按最小公约数取尺寸而
不是让最后一个连接赢。这里不选，只是标明它是第 4 期的阻塞项。

## 写操作

### 创建会话的幂等

**先说清楚它只解决一半问题。** `createSession` 已经是按名字幂等的：名字撞上已存在的
会话时它直接返回 `{ created: false }` 复用，不会起第二个（`src/tmux/session-create.ts`
的 has-session 分支）。所以带名字的创建请求重试多少次都只有一个会话。

`Idempotency-Key` 要覆盖的是**名字由服务端生成**的那条路径，那里重试确实会多出一个
会话。做法是在内存里保留最近 10 分钟的键到响应的映射，重试返回原响应。

因为适用面比看上去窄，它在分期里排最后，而且如果实现时发现所有创建路径都带名字，
这一条可以直接砍掉。

### 首行输入的语义

创建时可以带一行初始输入（模板机制）。契约必须写明：**注入前会等 agent 就绪，等超时
就放弃发送，而不是照发。**

超时意味着 agent 还没到能接收输入的状态——可能在装依赖，也可能停在「信任这个目录吗」
的确认框上。把排队的文字打进那个状态不会响亮地失败，它会安静地成功，作为对屏幕上那个
确认框的回答。响应里要能区分「会话建好了、首行也发了」和「会话建好了、首行没发」，
否则客户端没法把文字还给用户。

同理，当请求的名字撞上了已存在的会话（`created === false`，复用而非新建）时也不注入。

### 文本与原始字节分开

现在的 `POST /api/sessions/:name/keys` 收的是 `{text}`，走 `sendText`——名字在说谎。
契约里拆成两个：

- `POST /api/sessions/:name/input`，`{text}`。「打一行字进去」。
- `POST /api/sessions/:name/keys`，`{hex}`。原始字节，和 WebSocket 那侧对齐。

`/keys` 改变含义是个破坏性变更，但它是**响亮的**：旧的 `{text}` 请求体会直接 400，
不会静默地做错事。相比之下留着一个名不副实的路径，代价要一直付下去。

### 批量

`POST /api/sessions/keys` 和 `POST /api/sessions/input`，body 带 `targets: string[]`。
返回每个目标各自的结果，部分失败是正常情况而不是错误。

「给全部在跑的会话发一个 Esc」和「一次回答三个在等的会话」是舰队操作，让客户端循环
发 N 个请求既慢又没法表达「尽量都发到」。

### 删除

`DELETE /api/sessions/:name` 维持现状，包括它拒绝删除 `web-` 前缀的内部会话。写进文档。

## 能力协商

`GET /api/capabilities`：

```json
{
  "version": "0.x.y",
  "build": "...",
  "events": ["session.created", "session.ended", "session.renamed",
             "session.turn", "session.attention"],
  "streamEvents": ["resync"],
  "includes": ["preview", "items", "facets"],
  "features": ["webhooks", "sse", "idempotency-key", "batch-input"]
}
```

新客户端据此决定降级路径，而不是撞 404 再猜。这比版本号便宜，也比版本号诚实：它描述
的是这台服务器**实际**支持什么，而版本号只是一个需要查表的代称。

## 鉴权与暴露面

服务本身继续不做鉴权，回环绑定加反代是写进 `SECURITY.md` 的前提。这一条不变。

### 两个新的部署陷阱，要进 `docs/deploy.md`

1. **SSE 不能被缓冲。** 反代默认会攒够一块再吐，事件流会变成「几十秒一批」，看起来像
   服务端不发事件。Caddy 需要 `flush_interval -1`。
2. **SSE 是普通 GET**，所以 Basic Auth 能覆盖它——这点和 `/ws` 不同，`/ws` 那个坑
   （浏览器不在 WebSocket 握手时发 Basic Auth）已经在文档里了，不要因为相邻就混淆。
3. **现有的 `/ws` 鉴权方案是给浏览器设计的，原生客户端要知道这件事。** `docs/deploy.md`
   的做法是先在普通请求上种一个 cookie，WS 握手凭 cookie 放行，因为浏览器不会在握手时
   发 Basic Auth 头。一个原生客户端**没有这个限制**，它可以直接在握手请求上带 Basic
   Auth 头——但现网的 Caddy 规则只认 cookie，所以它反而必须去复现这套浏览器专属的舞蹈。
   契约文档要把这一段写明白，否则第二个前端的第一个 bug 就是「HTTP 全通，WS 403」。

### Webhook 带来一个新的形状，要进 `SECURITY.md`

服务器从此会**主动向外发请求**，目标 URL 来自一个没有鉴权的接口。

严格地说这不扩大攻击面：能碰到这个服务的人本来就能在里面跑 shell，SSRF 给不了他更多
东西。按 `SECURITY.md` 处理目录允许列表的同一个逻辑，加一层 URL 过滤是表演。

但有一件事是**真的新**：Webhook 订阅会**持久化**，它在建立之后持续把数据往外送，活得
比一次会话长。这是一个休眠的外发通道，和「能跑 ls」不是一回事。结论不是禁止，而是：

- 订阅列表必须在内置 UI 上**可见且可删**。看不见的外发通道才是问题。
- `SECURITY.md` 要有一段讲明白这件事，和讲 Jira 凭据那一段同样直白。

## 定稿前要还的债

这些是现有接口里不该被带进一个长期承诺的东西。

1. **`/api/dirs` 与 `/api/directories` 是两个不同的东西**——前者浏览目录加新建目录，
   后者返回 home 和最近用过的目录。名字像到几乎不可能不搞混。
2. **`/api/sessions/:name/keys` 收的是文本**，见上面的拆分方案。
3. **WebSocket 断开没有原因帧**，见 `{t:"exit"}`。
4. **`public/terminal.js:291` 的 `JSON.parse` 没有 try/catch**，一个畸形文本帧会在
   `onmessage` 里抛出去。

## 测试策略

- **事件总线**是 DOM-free 叶子模块，纯逻辑测试：状态变化才发、两个生产者不重复发、
  环形缓冲的挤出行为。
- **Webhook 的签名、退避、自动停用**同样是纯逻辑，脱离网络测。
- **SSE 端到端**用真 server：连上、触发一次状态变化、收到事件；断开后带旧
  `Last-Event-ID` 重连拿到补发；带一个过期 id 拿到 `resync`。
- **契约快照测试**：把对外字段集固定成 fixture，改了就红。这照搬本仓库
  `themes.test.ts` 逐键钉住深色主题的做法——那次的教训正是「所有断言都在测量比值，
  而比值从 3.01 挪到 3.07 依然通过」，一个契约字段被悄悄改名同样不会让任何行为测试
  变红。目的不是禁止改，是逼着改动说出口。

会话相关的集成测试继续遵守既有铁律：orphan 断言按 `web-${process.pid}-` 收窄，绝不
数整台机器的 `web-` 会话；只按精确名字清理自己创建的会话；绝不 `kill-server`。

## 未决问题

- **环形缓冲的大小**。按条数还是按时间？倾向于按时间（比如 5 分钟），因为客户端关心的
  是「我离开了多久」，而不是「这期间发生了多少事」。
- **轮询间隔是否要因为事件流而缩短**。事件的及时性现在受限于它。缩短会增加
  `capture-pane` 的负载，而那个负载是按会话数线性增长的。
- **token 用量要不要进会话资源**。来源是 transcript，所以拿得到；但它会让会话对象
  依赖一次额外的文件读取，而列表端点是每次页面加载都跑的。倾向于只放在
  `/api/sessions/:name/transcript` 里，不进列表。

## 分期

1. **服务端轮询循环（按需启停）** + 事件总线 + SSE + `/api/capabilities`。轮询循环是
   这一期真正的新东西，不要当成既有机制的接线。这一期最有价值，因为后面几期的价值都
   取决于客户端能不能便宜地知道「现在有事发生了」。
2. 会话资源整形（`include` 机制、单会话读路由、过滤、`/api/local/*` 迁移）+ 内置前端
   改成消费它。
3. Webhook。
4. 终端契约文档化 + `ready` / `exit` 两个控制帧。
5. 写操作（幂等、拆分 input/keys、批量）。

每一期自己带测试和文档。第 2 期是唯一会动 `public/` 的，风险最高，放在事件流之后是
因为那时候已经有一个真实的第二客户端视角可以用来检验形状。

### 第一个验证客户端是监察者，不是手机端

`plugins/supervisor/` 已经手工搓了一遍这套东西：它直接读 `~/.claude/projects/<编码 cwd>/
<session id>.jsonl`，直接 `tmux send-keys -t "=<session>"`，用 `/loop` 自己掐表巡视。
换句话说，**这份契约要提供的每一样东西，仓库里已经有一个消费者在用私有路径实现了。**

把它迁到契约上（transcript 读路由、`/input`、事件流代替 `/loop` 自定步调）有三重好处：
契约在任何手机端存在之前就被一个真实用户检验过；监察者的限制从「提示词级」往「代码级」
挪了一小步，因为它不再需要满机器找 jsonl；以及如果契约里缺什么，会在这一步暴露，而不是
等第二个前端写到一半才发现。

这不该排在五期之外，建议并进第 2 期做。
