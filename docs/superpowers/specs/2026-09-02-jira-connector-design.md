# Jira 连接器：手动同步把单拉进来

## 问题

首页现在有 13 张单，而分给你的 Jira 工单有 41 个。差的那 28 个不是 bug——第 1 期定的是「单是内核概念，Jira 只是来源之一，认领是显式动作」，迁移只把**已经开过会话**的 13 个绑定转成了单。

实际用下来这个默认是错的：**「分给我的单」本来就是你要看的东西**，而要求你为 41 个工单逐个点认领，等于把工具的工作交给人。

同时首页一次 Jira 都没访问过。`enrich` 跑在每次页面加载、300ms 硬预算里，明令禁止发网络请求，所以它只能读工单页碰巧填过的缓存——缓存冷的时候，首页上的单连状态和史诗都没有。

要的是：**一个同步动作**——按一下，把分给你的工单变成单，并带回 PR 状态。

## 已定的取舍

七条在设计对话里定死，不再重开：

- **拉回来的工单就落盘**，与本地单同等，不是"显示但不存"的候选。
- **工单从查询结果里消失时什么都不做**——不删、不自动归档，留在那里。（因此必须补手动归档入口，见下。）
- **启动时同步一次，之后手动触发，不做后台定时轮询。** 设计对话里一度定的是"内核后台定时拉"，后来推翻：先要能用，轮询以后再说。保留启动那一次，是为了开机/重启后首页直接是新的，不用你先按一下。
- **拉取范围由使用者在 Jira 配置里决定**，内核不预设，也不替它加条件。
- **内核只新增一个 `start()` 生命周期钩子**，且它当场就有真实消费者（启动同步）。其余全部走内核已有的 `ensureItemForSource`。
- **PR 状态只给有活跃会话的单拉**。
- **不做配置 UI**。`config.json` 仍然手改。

### 为什么内核这次一行新能力都不加

设计对话里先后否掉了两个更重的方案，理由都值得记下来：

**provider 契约**（新增 `provide()`，插件回答"我这儿有哪些单"，内核负责调度与入库）：被否是因为这个仓库的规矩——**「能力面按需要开，不按能想到的开」**。`annotate` 当初因为没有消费者被砍掉，有了真实消费者才开。provider 现在只有一个实现，为它造通用契约是推测性通用化；第二个数据源要复制的只是一次循环，那点重复远比一个过早定型的契约便宜。

其中一条支持它的理由被明确**收回**：曾说"插件调内核等于方向倒了"。这站不住——`plugins/jira/server.ts` 已经直接 import 了 `ensureItemForSource`、`bindSession`、`resolveBindings`，插件依赖内核正是既定且正确的方向。`ensureItemForSource` 本身就是"按 `(provider, ref)` 建或更新"。

**`start()` 钩子留下了，但它必须当场有人用。** 曾考虑只留接口、暂无实现，被否：那正是第 2 期 `annotate` 的处境——整整一期零实现者，最终复核把它记成"如果下一期滑票，就是被活测试守着的死代码"。所以钩子和它的唯一消费者（启动同步）一起落地。

## `start()` 钩子

`plugins/handlers.ts` 的 `PluginServer` 加一个可选能力：

```ts
export type PluginServer = {
  handle?: PluginHandler;
  enrich?: PluginEnricher;
  /** 进程启动时调一次。插件想在启动时做点什么，自己在这里做。 */
  start?: () => void;
};
```

内核对它的了解到此为止——不懂同步、不懂 Jira、不懂失败。只是"启动时给插件一次机会"。

**调用点在 `src/index.ts`，不在 `startServer()`。** 这条沿用第 1 期的教训：至少五个测试文件直接调 `startServer`，钩子挂在那儿就意味着跑一次 `bun test` 会拿真实 token 发请求、往真实的 `~/.tmux-next/items.json` 写单。迁移当初正是栽在这上面，`migrateJiraBindings()` 因此被移到 CLI 入口。`src/index.ts` 是唯一的 bin 入口，只有真启动才走。

一条守卫测试钉住落点：断言 `src/server.ts` 不 import 插件的 start 路径。跟第 1 期钉迁移落点那条同款——不钉住的话，一次"顺手收拢启动逻辑"的重构就能把它挪回去，而全套测试照样绿。

**不 await，也不让它挡住端口。** 迁移是 await 的，因为后面的正确性依赖它；Jira 同步不是——手机不该等 Jira。发出去就不管，`catch` 里记一条日志。

**失败语义仍然唯一**：`start()` 抛了或同步失败 = 这次没同步到，服务器照常起，单照常在。

## 同步动作

插件新增一条路由：

```
POST /api/jira/sync
```

它做四件事，全部用现成的东西：

```
按 config.jql 拉工单                  ← 已有的 fetchIssues
写进已有的 60 秒工单缓存               ← enrich 从这里读，不改
对每条工单 ensureItemForSource(...)   ← 已有，需加标题更新
给「有活跃会话」的单拉 PR 状态         ← 已有的 fetchDev，写进已有的 dev 缓存
```

返回 `{ created, updated, total, truncated }`，页面据此给一句反馈——按了之后什么都不说，跟坏了没区别。

**触发点在首页**，不在工单页：结果出现在首页，动作就该在那儿。放在顶栏，跟现有的刷新/设置按钮同一排。工单页保留它自己那套按单刷新，不动。

**同步是显式的、可能慢的。** 按钮要有进行中状态；失败要说清是凭据问题、查询问题还是连不上——这三类 `client.ts` 已经分好了，直接用，**不透传 Jira 的原始错误体**（里面带账号信息）。

### `ensureItemForSource` 要能更新标题

它现在是"有就返回、没有就建"，标题不更新——工单改了名首页就一直是旧的。加一个可选参数：

```ts
ensureItemForSource(provider, ref, title?, opts?: { refreshTitle?: boolean })
```

`refreshTitle` 只碰 `title`，**绝不碰 `cwd`、`tags`、`closedAt`**。那三样是本地状态，是你在这个工具里投入的东西，远端的一次改名不该动它们。这条要有测试，而不只是有注释。

**这是本次唯一改动内核的地方。**

### 一次同步最多建 200 张单

一条写错的 JQL 能返回几千条，而 `items.json` 是纯文本全量读写。超过就截断，并在响应里把 `truncated` 报出来、页面显示出来。

**静默截断会让页面看起来像"就这么多"**——这个仓库在 `checksKnown` 上已经守过同一条线：「我们没问到」和「没有」是两回事，收成一个会让页面往好看的方向撒谎。

### PR 状态只给有活跃会话的单拉

`jira.prs` / `jira.checks` 已经实现，但它们读的 `devCache` 只有打开工单页才会被填，所以首页上现在没有 PR。

全量拉的代价是：一个单一次 dev-status，每个 PR 再一次 Bitbucket。41 个单是上百次请求——这正是原设计拒绝开页即拉的原因。

所以只给**有活跃会话绑定**的单拉。这一条同时解决两件事：你真正盯着 CI 的那个 PR，一定是你正开着会话在做的那个；而请求数从"你有多少工单"（41，还会长）变成"你开着几个会话"（通常个位数）。其余的单在你打开工单页时按原有路径拉，一个字不改。

## assignee 维度

`Issue` 现在带 `{id, key, summary, status, statusCategory, updated, parent}`，没有 assignee。`client.ts` 要多要一个字段、多解析一个，`facetsFor` 多产一个 `jira.assignee`，`plugin.js` 的 `facetDims` 与两份字典各加一条。

这是这次唯一动到 Jira 数据形状的地方。

**取值可能只有一个，那不是问题。** 默认 JQL 是 `assignee = currentUser()`，此时这个维度只有你自己。筛选区是**按需添加字段**的，废维度不加就是了。想让它有意义就把查询放宽——那是配置的事，不是代码的事。

## 归档入口

「工单消失时什么都不做」意味着已完成、已转派的单会永久留在首页。必须有手动清理的办法，否则首页会慢慢烂掉。第 1 期给了 `closedAt` 和 `PATCH /api/items/:id`，至今没有 UI 能设它。

- 卡片上一个「归档」动作，写 `closedAt`
- 工具栏一个「显示已归档」开关，逐设备记住（跟分组、筛选、字段同一套 `localStorage`），关着时不画

**归档不是删除**：会话绑定、标签都在，取消归档就回来。这条继承第 1 期。

## 失败边界

单已经落盘，所以失败一律不影响你看到什么：

| 情况 | 行为 |
|---|---|
| Jira 连不上 / token 被吊销 | 单照常在，同步报错误，**绝不因为拉不到就删单** |
| 没配置 Jira | 同步路由返回"未配置"，跟工单页现有的表现一致 |
| 只拉回一半 | 无害——从不删，所以"这次没看到"和"不存在"不需要区分 |
| 超过 200 条 | 截断，`truncated` 报出来 |
| PR 那一步失败 | 单照常同步进来，只是少几个 facet。两步的失败互不牵连 |
| `start()` 抛了 / 启动同步失败 | 服务器照常起，端口照常开，单照常在。启动同步不 await |

"只拉回一半无害"是「消失时什么都不做」那条取舍换来的：内核不需要理解"一次拉取算不算完整"，也就不会把超时截断误判成工单失踪。

## 测试

- **`start()` 钩子**（内核）：一个会抛的假插件 → 服务照常起；一个正常的 → 只被调一次。用 `enrich` 那套注入假插件的做法，理由相同——注册表是编译期常量，没有注入就没法证明安全阀会触发。
- **落点守卫**：断言 `src/server.ts` 不 import 插件 start 路径。
- **同步循环**：抽成纯函数 `syncIssues(issues, ensure)`，无网络可测——标题会更新、`cwd`/`tags`/`closedAt` 不被碰、超 200 条截断且 `truncated` 为 true。
- **`refreshTitle`**（内核）：开着只改 title，关着不改；两种情况下本地状态都不动。
- **PR 只给有会话的单拉**：喂一批单加一批绑定，断言只对有活会话的那些发起 dev 请求。
- **assignee**：`facetsFor` 多一条断言。
- **同步路由**：未配置、凭据错、查询错、连不上四类各返回既有的分类原因，且不透传原始错误体。
- **归档**：happy-dom——点归档后卡片从默认视图消失，开关打开后回来。
- i18n 与主题：新键两种语言都要有且真被引用；新样式不许有颜色字面量。

## 不做

- **不做后台定时轮询**。使用者选的"先手工"。启动同步那一次是有的，轮询没有。
- **不做 provider 契约**（`provide()`）。真有第二个数据源时再看那时的形状。
- **不做写回 Jira**：不改状态、不写评论、不记工时。写操作发生在一个无认证的服务里，风险面完全不同。
- **不自动删单、不自动归档**。
- **不做配置 UI**。
- **不改 `enrich` 的规矩**：它仍然禁止发网络请求，仍然只读缓存。同步是另一条路，不是它的放宽。
