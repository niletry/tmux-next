# 数据源接缝：内核只认识来源，刷新交给来源自己做

## 问题

首页现在有 13 张单，而分给你的 Jira 工单有 41 个。差的那 28 个不是 bug——第 1 期定的是「单是内核概念，Jira 只是来源之一，认领是显式动作」，迁移只把**已经开过会话**的 13 个绑定转成了单。

实际用下来这个默认是错的：**「分给我的单」本来就是你要看的东西**，而要求你为 41 个工单逐个点认领，等于把工具的工作交给人。

同时首页一次 Jira 都没访问过。`enrich` 跑在每次页面加载、300ms 硬预算里，明令禁止发网络请求，所以它只能读工单页碰巧填过的缓存——缓存冷的时候，首页上的单连状态和史诗都没有。

要的是：**把单从外部系统同步进来，并且能单独刷新其中一张**——而这两个动作都要从首页发起，首页是内核代码。

## 已定的取舍

八条在设计对话里定死，不再重开：

- **拉回来的工单就落盘**，与本地单同等，不是"显示但不存"的候选。
- **工单从查询结果里消失时什么都不做**——不删、不自动归档，留在那里。（因此必须补手动归档入口。）
- **启动时同步一次，之后手动触发，不做后台定时轮询。**
- **拉取范围由使用者在 Jira 配置里决定**，内核不预设，也不替它加条件。
- **内核只认识"来源"，不认识任何具体插件。** 刷新交给来源自己做。
- **PR 状态只给有活跃会话的单拉**。
- **不做写回**：不改状态、不写评论、不记工时。
- **不做配置 UI**：`config.json` 仍然手改。

### 一次被推翻的判断，以及为什么

设计对话里先否掉了 provider 契约，理由是这个仓库的规矩——**「能力面按需要开，不按能想到的开」**：当时只有"同步"一个操作，且触发点在插件自己的页面上，插件直接调内核已有的 `ensureItemForSource` 就够了，造契约属于推测性通用化。

后来加了一条需求——**首页卡片上「刷新这一个单」**——这个判断就不成立了。首页是内核代码，而内核不能点名插件：它拿到一张单只知道 `source.provider === "jira"`，不能因此去打 `/api/jira/...`，那正是被反复守住的那条等式（"provider 名就是插件 id"）。要让内核的页面发起来源操作，就必须有一条泛型路径。

**所以契约不是被"想到"的，是被两个已点名的操作逼出来的。** 这跟推测性通用化的区别就在这里，值得记下来。

另一条被明确**收回**的理由：曾说"插件调内核等于方向倒了"。这站不住——`plugins/jira/server.ts` 已经直接 import 了 `ensureItemForSource`、`bindSession`、`resolveBindings`，插件依赖内核正是既定且正确的方向。

## 数据源接缝

### 插件在清单里声明自己认领哪些来源

```js
// plugins/jira/plugin.js
provides: ["jira"],
```

内核据此知道"谁负责这个 provider"，**而这张表是插件自己声明的数据，不是内核维护的名单**。这一步棋跟 `facetDims` 完全同源：`titleKey`、`legacyPaths`、`facetDims` 都是这么做的——凡是内核需要知道、又不该写死的东西，都由清单声明。

内核全程不出现 "jira" 这个词。`public/items.js` 里有一条测试断言它不含任何插件 id，这条继续有效。

### 服务端两个新能力

```ts
export type SyncResult = { created: number; updated: number; total: number; truncated: boolean };

export type PluginServer = {
  handle?: PluginHandler;
  enrich?: PluginEnricher;
  /** 进程启动时调一次。插件想在启动时做点什么，自己在这里做。 */
  start?: () => void;
  /** 把这个来源的东西同步成单。 */
  sync?: () => Promise<SyncResult>;
  /** 刷新单张单。ref 是 item.source.ref。 */
  refreshItem?: (ref: string) => Promise<void>;
};
```

### 内核两条路由

| 路由 | 行为 |
|---|---|
| `POST /api/items/sync` | 调所有声明了 `sync` 的插件，汇总成一个 `SyncResult` |
| `POST /api/items/:id/refresh` | 按 `item.source.provider` 找到 `provides` 里声明了它的插件，调 `refreshItem(item.source.ref)` |

**没有 `source` 的本地单不画刷新按钮**——没有来源就没有可刷的东西。找不到认领该 provider 的插件（插件被停用、来源来自已卸载的插件）时返回 404，页面据此不画按钮，而不是画一个必然失败的按钮。

**路由分派顺序**：`/api/items/sync` 必须排在 `^/api/items/([^/]+)$` 之前，否则 `sync` 会被当成一个 item id。这跟第 1 期 `/api/items/bind` 那条是同一个坑，当时就是靠顺序解决的。

### 安全阀

`sync` 和 `refreshItem` 都会发网络请求，所以**不能沿用 `enrich` 那 300ms 的预算**——那条预算是为"每次页面加载都跑"设的。这两个是显式动作，用**硬超时 30 秒**，`try/catch` 包住，失败归类后返回。

失败语义仍然唯一：**这次没同步到 / 没刷到，单照常在，页面照常出**。绝不因为拉不到就删单。

一个插件的 `sync` 失败不影响别的插件的——汇总时各算各的。

## `start()` 钩子

钩子留下并且当场就有消费者：`src/index.ts` 启动时调一次，Jira 的 `start()` 里调自己的 `sync()`。

**曾考虑只留接口、暂无实现，被否**：那正是第 2 期 `annotate` 的处境——整整一期零实现者，最终复核把它记成"如果下一期滑票，就是被活测试守着的死代码"。

**调用点在 `src/index.ts`，不在 `startServer()`。** 沿用第 1 期的教训：至少五个测试文件直接调 `startServer`，钩子挂在那儿就意味着跑一次 `bun test` 会拿真实 token 发请求、往真实的 `~/.tmux-next/items.json` 写单。迁移当初正是栽在这上面。一条守卫测试钉住落点：断言 `src/server.ts` 不 import 插件的 start 路径。

**不 await，也不让它挡住端口。** 迁移是 await 的，因为后面的正确性依赖它；同步不是——手机不该等 Jira。

## Jira 侧的实现

### `sync()`

```
按 config.jql 拉工单                  ← 已有的 fetchIssues
写进已有的 60 秒工单缓存               ← enrich 从这里读，不改
对每条工单 ensureItemForSource(...)   ← 已有，需加标题更新
给「有活跃会话」的单拉 PR 状态         ← 已有的 fetchDev，写进已有的 dev 缓存
```

**一次同步最多建 200 张单。** 一条写错的 JQL 能返回几千条，而 `items.json` 是纯文本全量读写。超过就截断，`truncated: true` 报上去、页面显示出来——**静默截断会让页面看起来像"就这么多"**。这个仓库在 `checksKnown` 上已经守过同一条线：「我们没问到」和「没有」是两回事。

### `refreshItem(ref)`

也是现成的：`refreshIssue(key)` 已经存在（重取一条工单并写回列表缓存），再顺带刷这个单的 PR/检查（`/api/jira/dev?refresh=1` 那条路已有）。

### PR 状态只给有活跃会话的单拉

`jira.prs` / `jira.checks` 已经实现，但它们读的 `devCache` 只有打开工单页才会被填，所以首页上现在没有 PR。

全量拉的代价是：一个单一次 dev-status，每个 PR 再一次 Bitbucket。41 个单是上百次请求——这正是原设计拒绝开页即拉的原因。

所以只给**有活跃会话绑定**的单拉。这一条同时解决两件事：你真正盯着 CI 的那个 PR，一定是你正开着会话在做的那个；而请求数从"你有多少工单"（41，还会长）变成"你开着几个会话"（通常个位数）。单张刷新不受这条限制——你明确点了那一个。

## `ensureItemForSource` 要能更新标题

它现在是"有就返回、没有就建"，标题不更新——工单改了名首页就一直是旧的。加一个可选参数：

```ts
ensureItemForSource(provider, ref, title?, opts?: { refreshTitle?: boolean })
```

`refreshTitle` 只碰 `title`，**绝不碰 `cwd`、`tags`、`closedAt`**。那三样是本地状态，是你在这个工具里投入的东西，远端的一次改名不该动它们。这条要有测试，而不只是有注释。

## assignee 维度

`Issue` 现在带 `{id, key, summary, status, statusCategory, updated, parent}`，没有 assignee。`client.ts` 要多要一个字段、多解析一个，`facetsFor` 多产一个 `jira.assignee`，`plugin.js` 的 `facetDims` 与两份字典各加一条。

**取值可能只有一个，那不是问题。** 默认 JQL 是 `assignee = currentUser()`，此时这个维度只有你自己。筛选区是按需添加字段的，废维度不加就是了。想让它有意义就把查询放宽——那是配置的事。

## 归档入口

「工单消失时什么都不做」意味着已完成、已转派的单会永久留在首页。必须有手动清理的办法。第 1 期给了 `closedAt` 和 `PATCH /api/items/:id`，至今没有 UI 能设它。

- 卡片上一个「归档」动作，写 `closedAt`
- 工具栏一个「显示已归档」开关，逐设备记住（跟分组、筛选、字段同一套 `localStorage`）

**归档不是删除**：会话绑定、标签都在，取消归档就回来。

## 失败边界

| 情况 | 行为 |
|---|---|
| Jira 连不上 / token 被吊销 | 单照常在，同步报分类后的错误，**绝不因为拉不到就删单** |
| 没配置 Jira | `sync` 返回"未配置"，跟工单页现有表现一致 |
| 只拉回一半 | 无害——从不删，所以"这次没看到"和"不存在"不需要区分 |
| 超过 200 条 | 截断，`truncated` 报出来 |
| PR 那一步失败 | 单照常同步进来，只是少几个 facet。两步的失败互不牵连 |
| 某个插件 `sync` 抛了 | 只是它这次没同步到，别的插件照常，汇总照常返回 |
| 单的 provider 没人认领 | `refresh` 返回 404，页面不画那个按钮 |
| `start()` 抛了 | 服务器照常起，端口照常开，单照常在 |
| 超时（30 秒） | 当作失败，同上 |

"只拉回一半无害"是「消失时什么都不做」那条取舍换来的：内核不需要理解"一次拉取算不算完整"，也就不会把超时截断误判成工单失踪。

## 测试

- **`start()` 钩子**（内核）：会抛的假插件 → 服务照常起；正常的 → 只被调一次。用 `enrich` 那套注入假插件的做法——注册表是编译期常量，没有注入就没法证明安全阀会触发。
- **落点守卫**：断言 `src/server.ts` 不 import 插件 start 路径。
- **来源分派**：一张 `provider` 无人认领的单 → 404；有人认领 → 调到那个插件的 `refreshItem`，且拿到的是 `source.ref`。用假插件注入，不依赖 Jira。
- **`sync` 汇总**：两个假插件，一个成功一个抛 → 汇总返回成功那个的数字，且不抛。
- **超时**：一个永远不返回的假插件 → 30 秒内返回失败，不吊死。
- **同步循环**：抽成纯函数 `syncIssues(issues, ensure)`，无网络可测——标题会更新、`cwd`/`tags`/`closedAt` 不被碰、超 200 条截断且 `truncated` 为 true。
- **`refreshTitle`**（内核）：开着只改 title，关着不改；两种情况下本地状态都不动。
- **PR 只给有会话的单拉**：喂一批单加一批绑定，断言只对有活会话的那些发起 dev 请求。
- **assignee**：`facetsFor` 多一条断言。
- **归档**：happy-dom——点归档后卡片从默认视图消失，开关打开后回来。
- **路由顺序**：`/api/items/sync` 不被当成 item id。
- i18n 与主题：新键两种语言都要有且真被引用；新样式不许有颜色字面量。

## 不做

- **不做后台定时轮询**。启动同步那一次是有的，轮询没有。
- **不做写回 Jira**。写操作发生在一个无认证的服务里，风险面完全不同。
- **不自动删单、不自动归档**。
- **不做配置 UI**。
- **不改 `enrich` 的规矩**：它仍然禁止发网络请求、仍然只读缓存、仍然是 300ms。`sync`/`refreshItem` 是另一条路，有自己的预算，不是它的放宽。
