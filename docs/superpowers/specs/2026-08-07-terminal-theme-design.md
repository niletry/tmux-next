# 终端配色主题

## 问题

终端的 16 色 ANSI 调色板从来没设过,一直吃 xterm.js 5.5.0 的默认值。从 `node_modules/@xterm/xterm/lib/xterm.js` 里挖出来,那是一套 **Tango**(GNOME Terminal 的配色):

```
#2e3436 #cc0000 #4e9a06 #c4a000 #3465a4 #75507b #06989a #d3d7cf
#555753 #ef2929 #8ae234 #fce94f #729fcf #ad7fa8 #34e2e2 #eeeeec
```

Tango 是为 GNOME 那种中性背景设计的,配上 tmux-next 的 `#14161a` 就偏暗:`color0` 对比度只有 **1.4:1**,几乎隐形。

同时 `ITheme` 有 23 个字段,`terminal.js:23` 只设了 2 个:

```js
theme: { background: "#14161a", foreground: "#e6e8ec" }
```

`cursor`、`selectionBackground` 全走默认。后者对"选中即复制"是核心交互反馈,不该听天由命。

还有一处隐患:`#14161a` 和 `#e6e8ec` 在 `terminal.js` 和 `style.css` 里各硬编码一份,改一处忘另一处就会露接缝。

最后:UI 里的 `--accent: #7aa2f7` 和 `--idle: #9ece6a` **本来就是 Tokyo Night 的蓝和绿**。也就是说 UI 已经在用 Tokyo Night 了,只有终端还停在 Tango 上——两者是脱节的。

目标:把终端拉回同一套配色体系,补齐 23 个字段,并让用户能在 UI 里换主题。

## 范围划分:什么跟主题走,什么不跟

外观里只有颜色需要"主题"这个概念,其余两类早就各就各位了:

| 类别 | 跟谁走 | 存哪 | 现状 |
|---|---|---|---|
| **颜色**(23 个 xterm 字段 + 页面外壳) | 主题,全局一套 | `~/.tmux-next/theme.json` | 硬编码,不可换 |
| **字号** | 设备 | `localStorage("termFont")` | 已实现,不动 |
| **列宽/行高** | 窗口,实时算 | 不存 | 已实现,不动 |

三类互不重叠:换主题不碰字号,换设备不碰配色,窗口变化两者都不碰。

所以**不需要"手机一套主题、桌面一套主题"**——手机和桌面的真实差异只有字号,而它早已按设备独立。配色两端共用一套,换手机不用重配。

区分原则:**"这台机器长什么样"存服务端,"这块屏幕多大"存浏览器。**

## 四套预设,以及为什么不照抄官方值

内置四套,默认 Tokyo Night(与现有 `--accent`/`--idle` 同源)。**每套带自己的官方背景**——One Dark 与 Nord 的标志性正是那偏亮的底,强行统一到 `#14161a` 会让它们失真。页面外壳通过 CSS 变量跟随。

按 WCAG 实测每套在**各自背景**下的表现:

| 主题 | 背景 | 正文 fg | 彩色最低 | 官方 brightBlack | 调整后 |
|---|---|---|---|---|---|
| Tokyo Night | `#1a1b26` | 10.6:1 | 6.5:1 | `#414868` 1.91:1 ✗ | `#6272a4` **3.63:1** |
| Catppuccin Mocha | `#1e1e2e` | 11.3:1 | 7.1:1 | `#585b70` 2.46:1 ✗ | `#7f849c` **4.44:1** |
| One Dark | `#282c34` | 6.6:1 | 4.4:1 | `#5c6370` 2.32:1 ✗ | `#7f8794` **3.86:1** |
| Nord | `#2e3440` | 9.2:1 | 3.1:1 | `#4c566a` 1.69:1 ✗ | `#7b8aa4` **3.58:1** |

两个发现:

**① `brightBlack` 四套全部不达标(1.69–2.46:1)。** 它正是 Claude Code 画次要信息的色——`⏵⏵ don't ask on`、`⎿` 前缀、时间戳,这个亮度在手机户外看不见。替换值全部取自各主题官方色板的更亮档(Tokyo Night 的 comment 系、Catppuccin 的 overlay1 等),色调不跑偏。作为参照,`style.css` 现有的 `--dim: #8b919c` 是 5.7:1。

**② 阈值只能定在 WCAG AA,不能定 AAA。** 初稿定的是正文 ≥7:1(AAA)、彩色 ≥4.5:1,实测下来 One Dark 正文只有 6.6:1、Nord 有两个彩色低于 4.5——**四套主流主题里有两套过不了**。照抄成熟配色再套 AAA 是不现实的。最终阈值:

- 正文 ≥ **4.5:1**(AA 正文标准)—— 四套实际 6.6–11.3,余量充足
- 彩色 ≥ **3:1**(AA 大文本/非文本标准;终端里的彩色多是 `✓`、`✗`、文件名这类短标记)
- `brightBlack` ≥ **3:1**

这套阈值仍然拦得住真正糟糕的配色——四套的原版 `brightBlack` 无一能过。

Nord 的彩色最低 3.1:1 是四套里最弱的,红绿区分度不如其他三套,看 diff 略吃亏。仍然收录,由用户权衡。

## 架构

```
public/themes.js          纯数据 + 纯函数，DOM-free，// @ts-check
   │                      四套 × 23 字段；themeNames() / themeVars(name)
   ├──→ theme-sheet.js    选择弹层：写 :root 的 CSS 变量
   │                      → 页面外壳与终端同时变色
   └──→ terminal.js       从 CSS 变量读，构造 xterm ITheme

src/theme.ts              服务端读写 ~/.tmux-next/theme.json（只存主题名）
   └──→ GET/POST /api/theme
```

**颜色值只在 `themes.js` 里存在一份。** CSS 变量由它写入,`terminal.js` 从 CSS 变量读回——消除了当前两处硬编码同一组值的隐患。

### 顺带清掉的一处语义错误

`style.css` 里 `#14161a` 出现 7 次,但其中 **5 处根本不是背景色**:

```css
.btn.primary      { background: var(--accent); color: #14161a; }
.chip.on          { background: var(--accent); color: #14161a; }
header .hbell.on  { background: var(--accent); color: #14161a; }
```

它们表达的是"**压在强调色上的文字色**",只是碰巧与背景同值。既然背景要随主题变,这个语义必须分开,否则换到 One Dark 时这些文字会跟着变浅、压在蓝底上读不清。

新增语义变量 `--on-accent`(每套主题各自定义),5 处替换掉;剩下 1 处真正的背景(`style.css:485`)改为 `var(--bg)`。

**为什么单独抽 `themes.js`**:它无 DOM 依赖,符合项目既有约定(`scroll-gesture.js`、`terminal-fit.js` 那批),可以 `// @ts-check` 并被 `bun test` 覆盖;`terminal.js` 那种 DOM 重的模块不做类型检查。

### 首屏不闪

主题名的权威在服务端,但 fetch 是异步的,首屏会先按默认色渲染再跳变。解法是 `localStorage` 缓存一份主题名:

1. 首屏同步读 `localStorage` 的缓存名,立即写入 CSS 变量 — 无闪烁
2. 随后 `GET /api/theme`,若与缓存不同则更新并回写缓存
3. 用户切换时 `POST /api/theme` + 更新缓存

`localStorage` 在这里只是缓存,不是权威——换设备时它为空,走服务端值,行为依然正确。

### 交互

复用项目已有的弹层模式(`create-sheet.js` 是同一套):

```
列表页顶栏齿轮 ⚙ → 弹层 → 点一套 → 立即生效（无刷新）
```

入口放列表页顶栏而非终端页工具栏:底部工具栏是高频操作区(⌨、粘贴、方向键),主题是设一次基本不动的低频操作。顶栏现有 4 个图标,加齿轮为 5 个,手机宽度放得下。

弹层里每套主题直接显示 8 个色块和一段仿真的 Claude Code 输出,点之前就知道长什么样。

## 测试

`src/themes.test.ts`,纯逻辑,不碰 tmux:

1. 每套主题 23 个字段齐全,无 `undefined`
2. 每个值都是合法 `#rrggbb`
3. **对比度回归**——每套相对**自己的**背景:
   - 正文 `foreground` ≥ 4.5:1
   - 彩色(`red`…`cyan` 及 bright 版)≥ 3:1
   - `brightBlack` ≥ 3:1
4. 默认主题名存在于主题表中
5. 每套都定义了 `--on-accent`,且它压在 `accent` 上 ≥ 4.5:1

第 3 条比配色本身更值钱:它把"好看"变成可验证的约束,以后谁再动配色(包括把新主题加进来),只要把可读性改坏,测试就会红。

`src/theme.test.ts` 覆盖服务端:未知主题名被拒、文件缺失时回落默认、路径可用 `TMUX_NEXT_THEME_PATH` 覆盖(遵循其余 7 个状态文件的既有约定,使测试不触碰真实 `~/.tmux-next/`)。

## 不做什么

- **不做自定义色**。放开 23 个色让人自己调,大概率调出一套对比度没人把关的配色。四套预设覆盖绝大多数偏好。
- **不做 `custom.css` 逃生舱**。真有深度定制需求再加,那时是几行代码的事。
- **不做明暗双主题**。四套都是深色;浅色底需要重新挑一整套 ANSI 值,且 tmux-next 的使用场景(夜里看手机)以深色为主。
- **不动字号与列宽逻辑**。它们已经各就各位。
